# D. Plugin-iframe ceiling and what makes it feel magical

Scope: how good can a plugin-iframe catalog (today `packages/plugin-dev/ai-view-builder`) get, and what makes a generative view feel magical. Read-only research, 2026-10-30. All paths are relative to the worktree root. Line numbers are from the branch HEAD (38cdebea12).

## 0. Bottom line

- A plugin-iframe catalog can look and move native for the core catalog (task cards, boards, grouped lists, metrics, planner-like days). It cannot be native for anything that needs host UI: context menu, schedule/estimate dialogs, global and task keyboard shortcuts, inline add-task, drag across the iframe boundary, live theme switching.
- Today's plugin is far below its own ceiling. The gaps that make it feel flat are mostly plugin-side and cheap: plain-text cards, full DOM rebuild per change, no skeleton or streaming inside a step, suggestion chips that still round-trip to the model, static theme snapshot.
- The "magic" is dominated by latency, not by rendering fidelity. Rank: instant local tier (no model call), then partial-UI streaming plus a skeleton, then model/effort choice, then card fidelity, then motion polish. Voice and contextual suggestions are second-order.
- Verdict: plugin-first is viable for the "magic" experience if the next work is latency and card fidelity. It is not viable as the end state for "native-feeling". Plan Decision B-now/C-later (`docs/plans/2026-10-30-generative-views.md`) stands. Confidence 70% (section 7).

### 1.2 Theme and UI kit

- `createPluginCssInjection` copies about 70 CSS variables from `document.body` once at build time (`--bg`, `--card-bg`, `--c-primary`, `--task-*`, `--s*`, shadows, transitions, font stack, scrollbar). `plugin-iframe.util.ts:121-250`.
- There is no theme-change message and no re-injection. A light/dark or theme switch while a view is open leaves the iframe on the old palette until it is reopened. Verified by reading the shim (`:253-575`): no `THEME` message type exists in `PluginIframeMessageType` (`packages/plugin-api/src/types.ts:1005`).
- UI kit (`plugin-ui-kit.css.ts`, 208 lines): reset for body, headings, buttons (`btn-primary`, `btn-outline`), inputs, table, `.card`, `.text-muted`, `.page-fade`. Basic controls only; no task row, chip, checkbox or icon.
- Icons: the host uses a Material Symbols webfont (`src/styles/font/material-icons.scss`). The iframe gets none; the plugin falls back to text glyphs (`render.ts:82,101`: checkmark, play, pause characters). Whether the host font is reachable through the srcdoc base URL is unverified and non-contractual (same-origin reach is exactly what #10150 would remove).

## 3. Performance with 500+ tasks (measured)

Method: realistic task objects, headless Playwright. Chromium same-origin `srcdoc` iframe with the real sandbox; WebKit is the Linux Playwright build, not iOS Safari. Bench files in `$TMPDIR/bench/` (outside the repo). Desktop numbers are a lower bound for phones; I assume phones are several times slower but did not measure that.

| What                                                                             | 500 tasks                | 2000       | 5000    |
| -------------------------------------------------------------------------------- | ------------------------ | ---------- | ------- |
| Node `structuredClone` of tasks                                                  | 5-6 ms (227-422 KB JSON) | 17 ms      | 45 ms   |
| postMessage round trip into srcdoc iframe (Chromium, incl. host-side creation)   | 2.2 ms median            | 8.1 ms     | 18.3 ms |
| `renderView` (full `replaceChildren` + FLIP), 4-column board, Chromium, two runs | 17-29 ms                 | 67-184 ms  | not run |
| Same, WebKit (Linux build)                                                       | 37-39 ms                 | 143-151 ms | not run |

Reading:

- The bridge is not the bottleneck. 500 tasks cost about 2 ms to ship. The `getTasks` payload is fine up to several thousand tasks.
- The renderer is. `root.replaceChildren(build(model))` rebuilds everything on any change (`render.ts:273`); 2000 cards is 11,616 DOM nodes. At 500 cards a rebuild alone exceeds one 60 Hz frame (16.7 ms) on a desktop and will exceed it clearly on a phone; at 2000 it is visibly janky.
- Fix without a framework: keyed in-place patch per card (compare `CardModel` fields, touch only changed nodes), plus `content-visibility: auto` with `contain-intrinsic-size` on `.card.task` or on columns so off-screen cards cost no layout/paint. Both are plugin-local. Real virtualization is only needed past roughly 2000 visible cards, which a generated view rarely shows (queries limit scope).
- FLIP already caps work: visible-only and at most 300 animations (`render.ts:8-9,216-218`). `measure()` calls `getBoundingClientRect` for every `[data-flip]` node (`render.ts:190-196`), which is O(N) forced layout before and after a rebuild; keying the patch would let FLIP measure only changed nodes.

### Latency anchors

- Nielsen Norman Group: 0.1 s feels instantaneous, 1 s keeps flow of thought, 10 s loses attention [P]. Plan target is first change within 2 s p50 (plan section 2). Rank 1 hits the 0.1 s tier; ranks 2-3 are what bring model-backed edits towards the 1-2 s tier.
- Nuance, not a rule: arXiv 2604.06183 (2026) found chat answers returned at a 2 s time-to-first-token were rated lower in thoughtfulness and usefulness than at 9 or 20 s on creation/advice tasks [P, chat-specific]. For direct manipulation of a UI the expectation is the opposite (instant is good), so keep fast edits fast but make new-view creation visibly "composing" (skeleton, staggered arrival) instead of snapping in.
- Claims that streaming makes responses "feel 40-60% faster" come from vendor blogs and are unverified [S]. I did not use them for ranking.
- Linear-style local-first, roughly 100 ms interaction feel is documented only by secondary sources [S]; consistent with the NN/g threshold, used here as direction only.

## 6. What a better plugin-only catalog looks like (smallest path)

Sequenced by impact over cost, each independently shippable:

1. Pre-baked specs for the four suggestions plus a skeleton on submit (latency rank 1-2, about 100-200 lines, no new dependency).
2. Card fidelity pass: tag chips and project dot (data already available through allowlisted calls), SVG checkbox and icons, 44 px touch targets, `touch-action`, safe-area, overdue emphasis, skeleton cards.
3. Keyed patch plus `content-visibility: auto` in `render.ts` (replaces the `replaceChildren` rebuild; keeps FLIP and focus restore). Solid is available as an alternative but is not necessary.
4. In-column reorder and auto-scroll in `drag.ts`.
5. Model default and effort per edit type, eval-gated; streaming partial props via `eager_input_streaming` behind a tolerant parser.
6. Optional small host additions, each reviewed under AGENTS.md "long-term cost": a theme-change message, a key-forwarding message, an `openTaskContextMenu(taskId)` method. These are the only way to close gap items 6, 8, 11 from inside a plugin; each widens the public plugin API, so propose them only if the product decision stays with plugin-first.

## 7. Verdict and confidence

Question: can a plugin-iframe catalog feel native?

Answer: yes for appearance, motion, responsiveness and the core interactions (done, track, open detail, drag within a board, optimistic edits). No for full parity: it will never share the host's context menu, schedule/estimate dialogs, global shortcuts, cross-list drag or live theme without new host API. The right framing for the plan is "native-looking and fast in a plugin, native-integrated in core later", which matches Decision B-now/C-later. Confidence 70%: high (about 85%) that the visual and speed ceiling is reachable in the plugin; medium (about 60%) that the "not magical" complaint is mostly latency and card fidelity rather than missing host integration, since I cannot see what the maintainer saw.

What I verified:

- Plugin-iframe creation, sandbox, theme snapshot, bridge, allowlist, and hook plumbing: `plugin-iframe.util.ts:23-35,37-89,121-250,253-575,599-618,623-908`; `plugin-index.component.html:67-78`; `plugin-bridge.service.ts:740,1252-1262`; `plugin-hooks.effects.ts:445-458`; `src/index.html:91-120`.
- Missing capabilities in the plugin API (no theme message, no key forwarding, no context-menu opener): `packages/plugin-api/src/types.ts:594,700-745,1005`.
- Plugin renderer, drag, edit loop, voice and commands: `ai-view-builder/src/ui/render.ts`, `drag.ts`, `app.ts`, `voice.ts`, `core/edit-loop.ts`, `core/commands.ts`, `core/model.ts`, `ui/index.html`, `manifest.json`.
- Native comparison: `task.component.html`, `board-panel.component.html`, `shortcut.service.ts:77`.
- Issues and PRs: #8467 / PR #8468 (cause and fix), #10150 (app:// follow-up).
- Measured: structuredClone, iframe postMessage round trip, and `renderView` cost in Chromium (two runs) and Linux WebKit (one run), numbers in section 3.
- Web sources: Anthropic prompt caching, latency and fine-grained tool streaming docs; NN/g response-time limits; arXiv 2604.06183; A2UI v0.9; View Transitions Baseline status.

What I am unsure about:

- Real device performance (iOS WKWebView, Android WebView). Linux WebKit is not iOS Safari; phone slowdown factor is an assumption.
- Real model latency for Opus, Sonnet and Haiku 5.5 on this prompt (no API key). The model ranking in factor 3 is a documented direction, not a measurement.
- Whether the host Material Symbols font loads inside the srcdoc iframe; View Transitions in Android WebView; WKWebView speech on current iOS.
- How the plan wants sub-tasks shown (nested or flat); I did not check that section of the plan.
- Prompt-starter and "feels faster" claims rest on secondary sources.

Risks:

- Any reliance on same-origin reach (host fonts, `window.parent`) breaks if #10150 lands. Keep the plugin on the bridge and inline assets only.
- Do not reintroduce a nested opaque-origin sandbox inside the plugin iframe: it can blank on packaged desktop (#8467).
- Streaming partial tool JSON can render invalid specs; apply only through the validated spec path, with rollback on failure.
- Each host addition in section 6 step 6 is a public plugin-API commitment (AGENTS.md "long-term cost of a change"); do not add speculatively.
- Switching the default model to a faster one without an eval risks lower first-try spec quality, which costs more time in retries than it saves.
- The task component is a hot path; this research does not recommend touching it. Any host-native renderer (the other agents' topic) must respect that.
