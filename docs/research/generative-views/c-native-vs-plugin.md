# Generative views: native components vs. plugin iframe

Read-only research, 2026-10-30. Worktree `feat/teleport-01rqkmg3-60fcc7`, branch `claude/generative-ui-todo-app-h4o6e8`.
Paths below are relative to `src/app/` unless they start with `packages/`, `docs/` or `/`.

## 0. Bottom line

Recommended: **option (a), a small, AI-agnostic "native view" host API, with every AI-specific part (prompt UI, model call, key, spec edit loop, spec persistence) staying in the bundled `ai-view-builder` plugin.** Keep (c) as the Phase 1 interim and as the escape hatch, reject (b), defer (d).

Why, in one paragraph: the task row, planner cards, board panels and charts are the "magic" and they cannot render inside an iframe. A look-alike costs ~1.1k lines in the plugin today and already drifts, while the real row is ~1.6k TS + 430 HTML + ~850 SCSS plus menus, swipe, DnD and the detail panel. The plugin infrastructure already has the right seam (the work-context embed slot plus `showInWorkContext`), so the host only needs to learn one new thing: "mount this declarative spec natively". That keeps AI out of core (the maintainer's constraint), keeps task data away from the model without any new permission machinery, and gives other plugins something reusable. The price is a permanent public plugin-API contract plus a catalog and a spec schema that must be versioned. That price is real and has to pass the "earns its place" test (section 6).

Confidence: **about 65-70%** (see section 8).

## 3. Minimal public API sketch (option a)

```ts
// packages/plugin-api/src/types.ts  (additive, optional on PluginAPI)
interface NativeViewSpec {
  specVersion: 1;
  root: string;                         // id of root node
  nodes: Record<string, NativeViewNode>; // flat, id-addressed (cheap to patch/stream)
  queries: Record<string, NativeViewQuery>;
}
// Nodes: stack | columns | taskList | board | metric | text | chart | heatmap
// Queries: scope, due, tags, projects, priority, text, sort, groupBy, limit
// No task ids, no titles, no actions: only structure + query parameters.

PluginAPI.showNativeView(spec: NativeViewSpec): Promise<NativeViewProblem[]>; // render in the embed slot
PluginAPI.updateNativeView(patch): Promise<NativeViewProblem[]>;              // optional: streaming patches
PluginAPI.closeNativeView(): void;
PluginAPI.validateNativeView(spec): NativeViewProblem[];                      // unresolved tag/project names, unknown node types
```

Host side: a lazy-loaded `<plugin-native-view>` standalone component mounted in the same slot as `<plugin-index>` (extend `workContextEmbed` so one slot holds either an iframe or a native view), resolving each query through a pure query engine (extracted from the customizer plus `doesTaskMatchPanel`), then mapping nodes to `board-panel`, a no-drop `task-list`, `planner-task`, `lazy-chart`, `heatmap`, metric tiles.

Host-side hardening required before a single spec can render safely:

1. A read-only / no-drop mode for `task-list` (avoid section-drop ops, `task-list.component.ts:709-740`).
2. A no-persist-order mode for `board-panel` (avoid orphan `updatePanelCfgTaskIds`, :228/:449/:534).
3. A pure `runViewQuery(tasks, query, startOfNextDayDiffMs)` extracted from the customizer (the root singleton cannot be parameterized per instance).
4. Selection-scope DOM markers so multi-select works inside the native view.
5. Suppress `board` `addTag` side effects for ephemeral specs.

Which other plugins could reuse it:

- `yesterday-tasks-plugin` hand-draws `.task-item` rows in a 411-line `index.html` (`packages/plugin-dev/yesterday-tasks-plugin/index.html:35,353`). It is the clearest second consumer: a spec with one `taskList` replaces it.
- `automations` (reports), `procrastination-buster`, `brain-dump` (list after capture), `sync-md` (status list), `app-auto-track` (time summary), `ai-productivity-prompts`.
- Any third-party "saved view / dashboard" plugin: that is the justification for it being generic and AI-agnostic. Honest caveat: this is a hypothesis; no issue or user report in this repo asks for it. The "earns its place" check (section 6) must be answered before building.

Why (b) is rejected, concretely:

- `@angular/elements` not installed; root deps rule forbids adding it without strong justification.
- `customElements` registry is per window. A cross-realm class extending the parent `HTMLElement` throws "Illegal constructor" in the iframe's registry.
- The Angular renderer uses the parent `DOCUMENT`, so component styles (emulated encapsulation, injected into the parent `<head>`) do not apply inside the iframe document.
- CDK drag-drop listens on the parent document and appends its preview to the parent body. Material overlays and menus attach to the parent body and need coordinate translation.
- The alternative "overlay a native element above the iframe" cannot sync scroll or FLIP animations.

## 6. Does option (a) earn its place? (feature-review-guide checks)

- **Demand**: not verified. No closed/open issue search was done in this pass. The strongest evidence is internal: two plugins already hand-draw task rows (`yesterday-tasks`, `ai-view-builder`) and the maintainer called look-alikes "not magical". Before building, someone must run the "closed issues" search the guide requires and count distinct requesters.
- **Leaner alternative**: ship the same `board-panel`/`BoardCfg`-based result entirely inside existing core (no new API) by letting the plugin create a real Board via a narrow `createBoard` action. Cheaper, but (i) it writes to the synced `BOARD` entity per user intent, (ii) it cannot express due-today / priority / text queries without extending `BoardPanelCfg`, and (iii) it pollutes the user's board list with throwaway AI views. It is the minimal alternative to surface; I judge it weaker than (a) for exploration but stronger for "accepted views".
- **Product principles**: "Avoid feature creep: extend existing building blocks" favors (a) over (d) (reuses the embed slot, `board-panel`, `planner-task`). "Less noise" is neutral. "Privacy" favors (a): queries resolve locally; the model sees only structure.
- **Plugin API permanence**: the new methods are a contract. To limit it: ship them behind an `experimental` marker in the types, keep `NativeViewSpec` small (`specVersion` literal, unknown nodes render as a placeholder not an error), and treat the catalog as additive-only.

## 7. Recommendation

1. **Now (Phase 1)**: continue with the plugin and the look-alike renderer; do not invest further in its fidelity. Add `specVersion` and keep the spec free of task data and action names (the plan already does).
2. **Next (Phase 2, ADR first)**: write an ADR for a generic `showNativeView(spec)` host API. Prerequisites in order: (i) extract `runViewQuery` as a pure function from the customizer and `doesTaskMatchPanel`; (ii) add a read-only mode to `task-list` and a no-persist-order mode to `board-panel`; (iii) a lazy `<plugin-native-view>` mounted in the existing embed slot; (iv) catalog of 5-6 items: `taskList`, `board` (via `board-panel`), `card` (`planner-task`), `metric`/`chart` (`lazy-chart`, `heatmap`), `text`, layout (`stack`/`columns`). Put the bridge wiring in a new file because `plugin-bridge.service.ts` is at its cap.
3. **Prove it with a second consumer**: port `yesterday-tasks-plugin` to the spec. If that does not feel right, the API is too AI-shaped and should not ship.
4. **Do not** build (b). **Defer** (d) until the maintainer's AI-in-core decision is made (`docs/market/README.md:28,74`); (a) is a strict prerequisite for (d) anyway, so nothing is wasted.
5. If the maintainer prefers zero new public API: fall back to (c) plus the minimal `createBoard` alternative above, and accept the fidelity gap.

## 8. Confidence

**About 65-70% that (a) is the right architecture; about 85% that (b) should be rejected; about 80% that (c) alone cannot reach the "magic" bar.**

What I verified:

- Embed slot and API: `plugin-bridge.service.ts:228-229,724-733`, `packages/plugin-api/src/types.ts:669`, `plugin-iframe.util.ts:34,37-89,121,623-645`, `plugin-security.ts:264-268`, persistence limits.
- `plugin-bridge.service.ts` is 2307 lines against a pinned cap of 2307 (`eslint.config.js:439`): zero headroom (earlier note said 17 under; the current count says none).
- No AI code in `src/app` (rg for anthropic/openai: zero hits).

What I am unsure about:

- **Demand**: no search of GitHub issues was done; the guide's closed-issue check is open.
- **Latency and spec validity** of the model edit loop, and whether native rendering of a streamed spec feels better than the plugin's FLIP renderer: unmeasured.
- Whether `task` / `task-list` can be hosted outside work-view without hidden dependencies (`WorkContextService.activeWorkContextId` reads in drop paths, `TaskMultiSelectService` DOM scope, `DropListService`). I found these by reading, did not run a spike.
- iOS plugin support was not verified.
- The 1.5-2.5k line estimate for core work is a judgement, not a measurement.
- Exact `plugin.service.ts:_getBaseCfg` line numbers and the `ai-view-builder` line counts come from earlier passes and were not re-counted here.

Risks:

- A permanent public API shipped before a second consumer exists locks in an AI-shaped design.
- Adding read-only/no-persist modes touches `task-list` and `board-panel` (hot path, sync-adjacent). A mistake there could regress real drag-and-drop ordering; needs E2E coverage on the existing work-view and board flows.
- The catalog becomes a maintenance commitment: every refactor of `board-panel` or `planner-task` now has an external consumer.
- "Task data never reaches the model" is a plugin design property, not a host-enforced guarantee, because plugins are unsandboxed. Do not market it as one without saying so.
- Multi-select, keyboard navigation (`TASK_CARD_LIST`) and Material overlays inside a plugin-driven container are untested.

## 9. Open questions

1. Is the maintainer willing to take a new public plugin-API surface (`showNativeView`) for this, given the permanence rule, or is "no new API" a hard constraint? That decision selects between (a) and (c)+`createBoard`.
2. Who is the second consumer? Without one, the API fails the "earns its place" test.
3. Should the native view live only in the work-context embed slot (project + TODAY contexts, in memory), or also in its own plugin route and the side panel? The slot is cheapest, the route is the more natural home for dashboards.
4. Should accepted views be promotable to real boards (one `addBoard` op), and if so, how does the spec map to `BoardPanelCfg` given the missing due/priority/text dimensions?
5. Is `task` (full row) allowed in the catalog at all, or only `planner-task` (lighter), given the hot-path rule and the 20-service injection graph?
6. What is the cap on rows per native view (virtual scroll vs. a hard limit) so a bad spec cannot render 5000 `task` components?
7. Does iOS run plugins, and does the native view work in the Android WebView with the plugin iframe also mounted (side panel + embed)?
8. Should `validateNativeView` return localized messages, or structured problems the plugin turns into prompt feedback for the model?
