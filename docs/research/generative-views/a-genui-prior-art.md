# Generative UI prior art, for SP "generative views"

Research date: 2026-10-30. Scope: what the generative-UI field has published about catalogs vs generated code, spec formats, data binding without the model seeing data, incremental edits, streaming, latency, catalog size, user reception and evals. Read-only research; no repo files changed.

Verification labels used below: **[P]** read from the primary source (vendor docs, repo, paper abstract) during this session; **[S]** secondary (blog, news, search summary); **[V]** vendor-authored benchmark or claim; **[U]** could not verify.

## 1. Bottom line for SP

1. The field has converged on three bands: **controlled** (pre-built components, model picks and fills props), **declarative** (model composes a spec from a catalog) and **open-ended** (model writes HTML/JS in a sandbox). CopilotKit, Thesys and Google's own products all say to mix bands, with open-ended as an escape hatch only. SP's plan (declarative now, sandbox later) matches the consensus. [P/S]
2. Nobody ships a **domain-level** catalog as a general product. A2UI's standard catalog is 15 atoms (Row, Column, Card, Text, Button, TextField...) and json-render's shadcn catalog is 36 atoms. The maintainer's idea (task row, planner task, kanban, grouped lists as components) is the "controlled band with a composition layer", which is where the best latency evidence sits (section 4).
3. The strongest analogue to "model never sees data" is a **decision-then-bind** architecture: the model (or a small decision model) chooses what goes on screen; code binds every value to a data path; nothing generates numbers (Very Good Ventures dashboard, median 54 s down to 3.8 s). [S, one vendor case study]
4. Latency is dominated by **output tokens**. Public numbers: Google's own Gemini dynamic view takes "a minute or more" and a reviewer reported waits up to 90 s; a frontier-model dashboard composer took a median 54 s. Nobody publishes a sub-2 s generative edit. SP's targets (2 s edit, 3 s first component) need an output budget of roughly 100 to 200 tokens per edit, which only high-level components plus patch edits can meet.
5. There is **no published eval of incremental edit accuracy** and none of catalog size effects specific to generative UI. SP's `eval/cases.json` harness is ahead of the public state of the art here.
6. Reception is split. One-shot answer UIs win preference studies (Google) but get called gimmicky when read-only, slow or rigid. Persistent, editable working surfaces over the user's own data pass the "does it help me steer" test. SP's idea is in the good quadrant; the current prototype probably fails on speed and richness, not on concept.

## 4. Answers to the specific questions

### Catalog vs generated code

- Declarative catalogs: A2UI, json-render, Thesys/OpenUI, Flutter GenUI, Tambo, Hashbrown. Generated code: Google dynamic view, Claude artifacts and Imagine, OpenIntelligentUI's sandbox. Hybrid and prebuilt: MCP Apps and OpenAI widgets (code, but written by the app author, not the model).
- Trade-off as stated by CopilotKit (vendor): controlled = highest consistency, lowest freedom; declarative = bounded by the catalog schema, "less pixel-perfect"; open-ended = "more error-prone, less predictable, slower, and more expensive". Thesys claims open-ended costs 5 to 10x the tokens of a declarative spec (no data given). [V/U]
- Security argument for catalogs is shared by A2UI ("safe like data, but expressive like code") and the json-render HN thread. For SP this is already satisfied.

### Spec format

- Flat id-addressed maps dominate (A2UI, json-render). Reasons given: progressive rendering, any arrival order, targeted updates. No source measures whether flat lists are easier for LLMs to emit.
- SP's `components` map keyed by id with `children` ids is the same family. No change needed.

### How data binds without the model seeing it

Five mechanisms exist:

1. **Client-owned data model with path bindings** (A2UI, json-render `$state`). The spec holds `{path: "/tasks"}`, never values. The data model is supplied by the app. [P]
2. **UI-only channel in the tool result** (MCP Apps `structuredContent`, OpenAI `_meta`). A standardised acknowledgement that UI data and model context differ. OpenAI warns `_meta` is not an authorization boundary. [P]
3. **Named query definitions executed on-device** (KX, Cherryboard, holotable, and SP's `queries`). Model emits a query spec; runtime executes; refresh needs no model. [S]
4. **Decision then bind** (Very Good Ventures): classifier answers closed questions, code binds values to paths, "nothing generates numbers"; the validator must check that data fits the block type, not only that it exists. [S]
5. **Return only user selections**, not data, to the model (`ui/update-model-context`, A2UI action context).

None of the surveyed systems resolve named entities ("the Work project") on the client from a model-emitted name; SP's name matching is novel ground. The closest precedent is schema-only dashboard builders, where the model sees table and column names. That leaks names, which SP's plan avoids by sending only the spec and the user's own words.

A nuance for the plan's "adopt A2UI wholesale" rejection (plan line 107, data bindings assume the agent supplies data): that is the usual flow, but the data model is client-held, `sendDataModel` is opt-in, and v0.9 allows custom catalogs, so a `TaskList` or `Board` custom component bound to a client-seeded path is plausible. [U: no doc statement that a client may seed the model.] It is still not worth adopting wholesale (pre-1.0, churn from v0.8 to v0.9 to v1.0 RC), but an A2UI custom-catalog export is a credible later path.

### Incremental edits and streaming

- Best precedents: A2UI id-upsert; json-render's three edit modes (RFC 6902 patch default, RFC 7396 merge, unified diff) with the current spec in the prompt; AG-UI JSON Patch deltas. Claude artifacts' `update`/`rewrite` split shows the failure mode: exact-match edits fail on large changes. [S]
- SP's `put_component` (merge by id), `remove_*`, `set_view` is already the A2UI approach plus a merge. The gap is not protocol; it is edit size and speed.
- Streaming: Anthropic's `eager_input_streaming: true` per tool delivers tool input fragments without server-side buffering or validation, so partial or invalid JSON is possible and must be accumulated and guarded. [P, GA on current models] MCP Apps defines best-effort repaired partial args (`tool-input-partial`), and describes them as best-effort. Tambo/Hashbrown/json-render render skeletons or fallbacks while props are undefined. OpenUI Lang's forward references let a layout skeleton precede its children.

### Catalog size and component selection

- No generative-UI-specific measurement found. Related: LongFuncEval (arXiv:2505.10570) reports function-calling performance dropping 7% to 85% as the tool catalog grows (catalog sizes not retrieved). [P abstract] Secondary summaries cite 92.4% to 78.2% selection accuracy from 15 to 640 tools and practitioner "safe zones" of 10 to 20 tools per context. [S/U]
- Vendor guidance: LangChain says keep catalogs focused and write specific descriptions; the model reads the description to decide when to use a component. Hashbrown rejects duplicate names so one tag cannot resolve to two components. OpenAI says tool descriptions must say when to use the tool. [P]
- Scale check: A2UI's complete schema plus catalog is about 8.8k tokens. A 20 to 40 component SP catalog with short descriptions is the same order of magnitude or smaller. At that size, count is unlikely to be the accuracy limiter; overlap between components and ambiguous prop semantics probably are. [Inference, not measured]

### Latency techniques

Evidence-backed:

1. **Cut output tokens.** Latency scales with tokens; use high-level components and edits instead of regenerating. At the 60 tok/s OpenUI assumes (not a measured Claude rate), 2 s is about 120 tokens, 3 s about 180, 8 s about 480. Vendor-run totals show multi-hundred to multi-thousand token outputs even in a compact DSL (section 3), so a dashboard built from atoms is unlikely to meet SP's 8 s target; one built from domain components plausibly can. [Inference]
2. **Move closed decisions out of the model** (VGV: 54 s to 6.1 s with router plus small model, 3.8 s with a decision model).
3. **Smaller model, lower thinking** when everything needed is in the prompt (VGV recommendation). Local small models fail format compliance (a2ui-bench), so test Claude small tiers on SP's own cases rather than assume.
4. **Prompt caching** of tools plus system (Claude: cache prefix order is tools, system, messages; reads cost 0.1x base, 0.05x on Sonnet 5.5 and Opus 5.5; 5 minute default TTL, 1 hour option; minimum cacheable 512 tokens on Sonnet 5.5 and Haiku 5.5). Any tool-definition change invalidates all three layers. [P]
5. **Fine-grained tool streaming** (above).
6. **Pre-generated templates** reviewed offline: practitioner guides (unverified) call offline-generated templates the lowest-latency option; the ajing post favors quick-action shortcuts over generation. No measured numbers.
   Not evidenced: speculative decoding or fine-tuned UI models for this task.

## 5. Transferable patterns for SP (8)

1. **Domain components with a thin layout layer, not atoms.** Catalog of a few coarse, non-overlapping components that map to existing SP building blocks (task list with groupBy/sort/fields, board, planner day/week, time-report metric, text) plus 2 to 3 layout containers. Reason: output tokens dominate latency (section 4); atoms like A2UI's Card/Row/Text would make every task row model-authored and un-SP-like; the VGV lesson is that the model's real job is "what goes on the screen", not typing markup. Keep component descriptions short and mutually exclusive ("when to use / when not to").

2. **Recipes: one call for the common 80%.** Add a small library of named view recipes (kanban of a project, weekly review, today plus tracked time, Eisenhower) that the model selects and parameterizes in one tool call (`apply_recipe` with a few args), with `put_component` for free composition and edits. Reason: the field's pattern is "select then compose": CopilotKit says mixing bands is the right architecture; Google ships "visual layout" next to "dynamic view" in the Gemini app (whether it is template-based is unverified); VGV got from 54 s to under 6 s by turning composition into classification. Recipes also make first paint near-instant and are testable fixtures.

3. **Data by reference, resolved on the device.** Keep the spec value-free (queries, name references), run queries locally, and keep tool errors structural. Reason: this is the dominant privacy pattern (KX, Cherryboard, holotable, A2UI paths, MCP `structuredContent`), and it gives free refresh with no model call. Add VGV's lesson: the validator must check that data fits the block type, not just that it exists. A query that resolves to zero tasks, an ambiguous project name or a column predicate that matches nothing should render as an inline, user-visible state; do not send counts or names back to the model unless the user opts in. A local fuzzy match plus a disambiguation chip beats a model round trip.

4. **Edits as small id-addressed patches.** Keep merge-by-id and `remove_*`; add RFC 7396 style null-deletes if not present; send the current spec in a compact normalized form; reserve `set_view` for new views. Reason: A2UI and json-render converge here, and Claude artifacts show that exact-string or whole-document edits fail at scale. Measure edit size in output tokens in the eval; the ceiling is about 120 tokens for the 2 s target.

5. **Stream tool args and paint skeletons first.** Use `eager_input_streaming`, parse repaired partial JSON for display only, and commit on block close (as the plan already does). Emit order: root and containers first, leaves after, so the shell appears while rows fill; render a placeholder for ids referenced but not yet defined (A2UI buffers until `root`; OpenUI Lang forward references; json-render `loading`). Reason: perceived latency is the first visible change, and every system that streams does it this way.

6. **Cache the catalog, keep the prefix stable.** Put tool definitions and the catalog prompt in a byte-stable prefix with `cache_control`, use the 1 hour TTL because users edit in bursts, and put the current spec and the request after it. Reason: cache reads are 0.05x to 0.1x input price and shorten prefill; A2UI-class prompts are around 9k tokens, so this matters. Never reorder or edit tool text per request (any change invalidates all layers).

7. **Self-repair as a first-class, measured path.** Return validation failures as tool errors (OpenUI ships Autofix with one extra call; A2UI v0.9 is prompt-first and relies on post-generation validation with errors fed back; the plan already allows at most 4 rounds), accept lenient envelopes, and report **completion rate** (non-empty, valid, rendered) before latency in the eval. Reason: a2ui-bench near-zero scores were format compliance, VGV saw 6 of 15 malformed turns, and VGV noted that a lenient renderer hides failed generations, which is why they validate independently. Run thinking on and off per model.

8. **Make views steerable surfaces, and show what changed from the applied steps.** Keep interactions on real data (check, drag, track) and avoid read-only widgets; pair them with a one-line change summary generated from the steps actually applied (not the model's prose), plus undo. Reason: the "steering test" (ajing, author's opinion, no study) ranks editable working objects as useful and read-only reports as gimmicky; "Design Theater" (arXiv:2607.22928, 24 tasks, 120 interfaces, 5 tools) found over 25% of stated design rationales (34% for functional ones) were not implemented; LEGOUI (arXiv:2608.04293, N small) found inspectable intermediate representations raise perceived control.

## 6. Pitfalls

- **Atomic catalogs feel generic.** The field's catalogs are atoms; copying them yields cards and text boxes, which is the "not magical" feeling. Domain richness has to come from SP components.
- **Slow is the default failure.** Frontier models with thinking and 1k+ token outputs land at 20 to 90 s in every public report. Do not default to the largest model for edits.
- **Format fragility is the main reliability risk**, not component choice (a2ui-bench, VGV). Budget for lenient parsing and repair.
- **Prose that claims changes not made** (Design Theater). Derive user-facing summaries from applied steps.
- **Vendor benchmarks flatter DSLs.** OpenUI's 52% fewer tokens is against verbose JSON; a compact fixture showed 300 vs 322 tokens. A custom DSL needs a parser, streaming logic and a prompt; with tool-call JSON args that is YAGNI until measured on SP's own catalog.
- **Spec churn.** A2UI went from v0.8 (structured-output first) to v0.9 (prompt-first, new envelope) to a v1.0 RC (adds `actionResponse` RPC, renames theme to `surfaceProperties`) within a year of public release; json-render is self-described as an early research prototype; MCP Apps spec is dated 2026-01-26. Keep SP's spec its own versioned contract with an export path.
- **Name references leak or fail.** Schema names can be sensitive (essay cited in section 4); ambiguous or renamed names fail visibly. Pinning ids is a later field, as the plan says.
- **Open-ended code later = dead buttons.** Imagine with Claude testers reported controls that did nothing; keep any sandboxed block as an escape hatch with narrow bridges, as MCP Apps does (different-origin sandbox, explicit CSP).
- **Unstable output for repeated tasks.** Views the user returns to should not be regenerated per visit; SP persisting specs already avoids this.
- **One-shot preference studies overstate value.** Google's Elo result ignores speed and tests query answering, not recurring personal tooling (Nielsen's own caveats). Do not treat it as evidence that views will feel good at 20 s.
