# Make sync boring

> **Status: Proposed.** Planning only; no app code changes with this document.
>
> **Owner / tracking:** Unassigned. Tracker [#10393](https://github.com/super-productivity/super-productivity/issues/10393), findings [#10382](https://github.com/super-productivity/super-productivity/issues/10382).
>
> **Last verified against the code:** 2026-11-09, master `3d2cdcf2b3` (one sync-path commit after `v20.0.0`).
>
> **Removal condition:** delete once the four sync services are under the 1200-line cap and the work queue in § 5 is shipped or declined; move anything still open to the tracker.

"Boring" means three things: users rarely see sync fail, the files are small enough to review, and a change is cheap to verify. This plan measures where each stands today, lists what is left by evidence, and gives a queue of one-session, one-PR items.

**Sections:** [1 Current state](#1-current-state) · [2 Definition of boring](#2-definition-of-boring) · [3 Failure classes](#3-remaining-user-visible-failure-classes) · [4 Structural track](#4-structural-track) · [5 Work queue](#5-work-queue) · [6 Open decisions](#6-open-decisions-for-the-maintainer) · [7 How this was measured](#7-how-this-was-measured)

## The short version

- **The pause did not happen.** The tracker says sync stabilization has been paused with an empty queue since 2026-10-06. Since that day 39 fix commits landed on sync paths, and about three in four trace to maintainer-filed findings, not user reports (§ 1.1).
- **The code is still growing.** Production code in [op-log/sync](../../src/app/op-log/sync/) went from 18,337 lines (2026-09-26) to 21,810, +19% in six weeks.
- **None of the four oversized services has been split.** They sit at their caps, so each fix has to squeeze in or land in an uncapped `*.util.ts`.
- **The open user reports are mostly not about conflict resolution.** They are about encryption passwords, Dropbox on iOS, and Android networking, on providers that have no E2E harness (§ 3).

So the plan is: hold the intake bar for real, split the four services as pure moves, and work only the handful of items that have user evidence.

## 4. Structural track

### 4.1 Rules for every split

The precedent is #10621: whole methods moved, the public API kept through thin delegating methods, the spec almost untouched.

1. **One cluster per PR, one file per PR.** No behaviour change, no renames, no reformatting of moved code.
2. **The old service keeps its public methods** and delegates. Callers, specs and the fuzz harness do not change. This matters: [the fuzz harness](../../src/app/op-log/testing/integration/sync-fuzz/sync-fuzz-harness.ts) patches `forceDownloadRemoteState` on the service instance, and 51 files inject the store.
3. **The existing spec file stays where it is** and must pass without edits beyond DI providers. Splitting 5,000–9,000-line specs is not part of this track.
4. **Lower the cap in the same PR** to the new line count in [eslint.config.js](../../eslint.config.js); delete the entry once the file is under 1200.
5. **Never split a file that an open sync PR touches.** Land or close that PR first.
6. **Verification, the same every time:**
   - `git diff --color-moved=dimmed-zebra` shows only moves plus delegates.
   - `npm run checkFile` on touched files and `npm run typecheck`.
   - `npm run quiet -- test:affected`.
   - `npm run sync-fuzz:compare`: 0 newly failing, identical steps.
   - One E2E smoke per provider family the file serves (named per step below).

A pure move does not shorten a method. Six methods are longer than 250 lines (`_syncBody` 760, `_processDownloadResult` 660, `forceDownloadRemoteState` 380, `uploadPendingOps` 335, `_downloadOps` 320, `_uploadOpsSplit` 280). Breaking those up is a behaviour-risk refactor and is out of this track (decision 5).

### 4.6 Order

### What not to do, and why

- **No new audit, sweep or fuzz-profile work while the structural track runs.** Each sweep has produced findings, each finding a fix, each fix the next edge case. Item 10 measures; it does not open work.
- **No fix for a § 3 gap without a user report.** That includes the remaining fail-closed crossings, whole-entity LWW loss and restart divergence.
- **No v3 default, no v2 retirement, no new v3 features** until decision 2. Splitting the adapter first makes either choice cheap.
- **No trigger consolidation.** The audit deferred it, its gates are unproven, and it changes latency and request counts for no reported problem.
- **No per-field timestamps, order merge, CRDT, server-side resolution or schema bump.** D2, D4, D5 and D11 stand.
- **No persistence consolidation and no SQLite.** No user report points there.
- **No server-side version-floor enforcement** until a named payoff exists (#10397, already deferred).
- **No moving code into `packages/` as part of a split.** That changes [package boundaries](../sync-and-op-log/package-boundaries.md) and is a separate decision.
- **No spec-file splitting and no method decomposition inside a move PR.** They make the move unreviewable.
- **No Dropbox, OneDrive or LocalFile E2E harness.** It would be large new test infrastructure; the narrow real-path rule covers these providers. Revisit if class C turns out to be provider-specific.
- **No Unicode normalisation of passwords.** It was declined as incompatible with the released fleet; U1 does not need it.

## 6. Open decisions for the maintainer

1. **Does the third intake bullet stay as it is?** It admitted about 30 maintainer-found fixes in five weeks. **Recommendation:** for the duration of the structural track, a maintainer-found reproduction becomes an issue, and at most two per month are fixed, chosen by harm. User reports and master regressions are unaffected.
2. **Which file format is the future?** v2 is the default again and v3 is opt-in with four open readiness fixes (#10395). **Recommendation:** keep v2 as default, freeze v3 (bug fixes for existing v3 users only), and decide after the adapter is split along that line.
3. **Do structural PRs count toward the cap of five?** **Recommendation:** yes, with at most two open and never two on one file.
4. **Should U1 ship?** The issue thread records the unchecked save as known and not fixed. **Recommendation:** yes; it is the only certain mechanism behind the most-confirmed open sync report, and the fix is a check, not new protocol.
5. **Are the non-pure steps (W5, W6, P4, P5) and breaking up the six long methods allowed as standalone refactors?** **Recommendation:** W5 and W6 yes, after the pure moves, one per PR. P4, P5 and method decomposition only when a user-evidenced fix needs to change that code.
