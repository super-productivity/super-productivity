# Sync-trigger consolidation preflight — 2026-09-26

**Baseline:** published master `8306d3adfc0fa2ad5feacb3aa6bb3e7be309161a` (includes #10267), verified against `origin/master` at the start of the audit. Sources were read from `git show` and an isolated archive of that SHA, not this worktree's inherited `9177c3afed6429934632b23de936cda8c6603fde`. All source links below pin the audited commit. Product code is unchanged; existing fixes and S1–S8 work are outside this audit.

**Verdict: defer the combined collapse.** A smaller WebSocket-only consolidation remains plausible, but Task 3 does not yet supply all the eligibility, initial-gate and settlement guarantees assumed by Tasks 4–5. Replacing immediate upload also adds a GET to every ordinary local burst and puts remote catch-up ahead of upload. Neither that latency cost nor the additional adapter work has been justified by demonstrated net simplification. This is a bounded preflight, not authorization to implement either change.

**Request counts for one debounced local burst**

These are **source-derived counts**, not runtime measurements or an after-implementation benchmark. Assume an established, ready, encrypted SuperSync client with durable cursor > 0, stable remote data, ordinary compatible operations on non-conflicting entities, no snapshot/migration/rejection/recovery, and no concurrent triggers. Count logical provider GET/POST calls; cursor/config reads are local storage. One burst means one immediate-upload invocation versus one invocation of today's full-sync wrapper.

| Starting backlog                                                                 | Current immediate upload                 | Today's full sync         | Difference / completion                                                                                                        |
| -------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Idle, no pending local or remote ops (a queued burst already consumed elsewhere) | 0 HTTP calls                             | 1 GET, 0 POST             | +1 GET; without any trigger both paths do nothing.                                                                             |
| `n > 0` local ops, no remote backlog                                             | `ceil(n/25)` POST                        | 1 GET + `ceil(n/25)` POST | +1 GET; 1–25 ops: 1 → 2 requests; 26 ops: 2 → 3.                                                                               |
| 1 local op + 1,001 remote ops                                                    | 1 POST; up to 500 remote ops piggybacked | 3 GET + 1 POST            | 1 → 4 requests for this invocation; full sync catches up all 1,001 before uploading, immediate leaves 501 for a later trigger. |
| 0 local + 1,001 remote ops                                                       | 0                                        | 3 GET                     | Different work: immediate upload cannot initiate remote catch-up alone.                                                        |

Derivation: [upload][upload] returns early for no pending ops and chunks API uploads at 25; [download][download] loops over 500-op pages; [server GET][server-get] uses one-row lookahead, so no extra empty terminal GET is needed. [Server POST][server-post] piggybacks at most 500 per chunk. [Wrapper][wrapper] downloads before upload. In the 1,001-op example a later catch-up needs two GETs after immediate upload, so comparable eventual catch-up is 3 total calls versus 4, provided that later trigger occurs; the immediate path itself schedules no download merely for `hasMorePiggyback`.

Bounds are conditional: a normal pass checkpoints after 50,000 new ops or 1,000 pages and schedules another run; already-applied history can increase pages per new op. Full sync allows its initial upload plus three reconciliation passes, each potentially many POSTs; immediate upload allows one local-win follow-up. Rejections can invoke additional normal and forced downloads. Cursor-zero migration probes (`downloadOps(0, undefined, 1)`), snapshots, gap resets and recovery are outside the table. [Web][http-retry] and [native][native-retry] transport permit two retries of eligible transient network failures: up to three HTTP attempts per logical call, not a fixed whole-burst bound. See [migration][migration], [constants][constants] and [rejections][rejections].

Latency is unresolved, but its direction is explicit: retain the two-second local debounce, then wait for occupancy and any remainder of the five-second settle floor, then pay download/page/apply time before uploading. A WS replacement likewise inherits the floor instead of only its current 500ms debounce / 250ms busy polling. The existing live push test requires propagation in under 10s; no measurement here proves that a two-client replacement meets it. Do not hide this cost by introducing upload-only policy inside the scheduler.

**Notification and durability audit**

| Surface                                     | Current behavior and required boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Advertised sequence versus durable progress | WS takes the maximum before 500ms debounce and retains a pending sequence through busy/in-flight work. It skips when `getLastServerSeq() >= latestSeq`, but clears pending **before** downloading and does not re-read the cursor after success. Generic success is therefore not proof that the advertised sequence was committed. Keep a thin adapter that clears only on durable progress; do not bless dropping outstanding work as compatibility.                                                                                                                                                                                                                                                                                                                    |
| Pagination                                  | Ordinary downloads already page through the backlog. A capped pass emits `remoteBacklogRemains$`; `SyncEffects` queues full sync, including when the download originated from WS. Thus “one successful page loses the remainder” is not an accurate current failure claim. Both top-level paths opt into keeping a decrypted prefix before reporting a later decrypt failure (#9256); forced/rejection downloads do not. Incompatibility, deferred repair or apply failure can still leave a cursor behind; preserve those recovery/status semantics.                                                                                                                                                                                                                     |
| Retry / exhaustion / wakeup                 | Transient throws requeue at 1s, 2s, 4s (four attempts total). Exhaustion reports ERROR and does not retain the attempted watermark in the pending slot unless another notification arrived. The subscription-wide `scan` remembers its maximum until stop, so a later notification can revive it; there is no dormant timer, reconnect or full-sync-settlement wakeup. Existing WS spec explicitly asserts no fifth attempt after 60s. This proves retry policy, not permanent user-data loss.                                                                                                                                                                                                                                                                            |
| Transport / auth / configuration            | [Transport][transport] owns heartbeat and reconnect (up to 50 attempts, exponential 1–60s with jitter); 4003 auth, 4008 limit and 4009 replaced close codes stop automatic reconnect. It exposes connectivity, not an auth-suspension event to the adapter. Adapter stops on HTTP auth/missing-credentials errors, not the terminal WS close itself. [Wrapper cleanup][ws-lifecycle] watches configured provider ID, not same-ID account changes or enabled state; queued WS work captures provider/epoch only at drain. Old-account watermark isolation is therefore an unproven contract, not something the new scheduler alone fixes. Reconnect's [server `connected` message][server-ws] advertises no cursor; a later successful full sync can explicitly reconnect. |
| Local wins / restart                        | WS uploads once when download creates local-win ops; immediate upload permits one follow-up. Full sync's bounded loop already owns local-win and transient-rejection reconciliation. Preserve ERROR/UNKNOWN outcomes instead of silently losing re-uploads. WS stop/restart clears in-memory watermark/retry state; startup full sync recovers from the persisted per-target cursor. The pinned live push test checks neither durable cursor nor reload.                                                                                                                                                                                                                                                                                                                  |
| #10267 forced-download resume               | [Download][download] now resumes only rejected-op forced re-delivery, keyed by client ID + `configEpoch`, retaining merged clocks and snapshot clock. Checkpoints advance only while no new op has been collected; a new/unapplied page is fetched again. Cursor movement does not invalidate the checkpoint; config/identity changes do, gap reset clears it, completion clears it, process restart loses it. A newer resumed snapshot replaces the saved snapshot clock. Forced full-history cap exhaustion still fails closed. This is separate from ordinary durable-cursor paging and must stay in the shared download service.                                                                                                                                      |

These are source-backed contract gaps, not newly reproduced end-to-end data-loss bugs. A corrective implementation needs a real-shape failing E2E first; no mocked “success below watermark” result alone establishes a current app failure.
