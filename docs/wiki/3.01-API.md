# APIs

This reference is the entrypoint for working with Super Productivity's APIs. The app exposes **four API systems**: the **Sync Server REST API** (for data synchronization), the **Local REST API** (for controlling the desktop app from local scripts, with an opt-in **MCP endpoint for AI assistants**), the **Plugin API** (for extending the app), and **URL Scheme Actions** (for triggering a handful of task actions from outside the app, e.g. an iOS Shortcut). This reference summarizes all four; full request/response schemas and examples live in the repository (Sync Server: `packages/super-sync-server/`; Plugin API: `packages/plugin-api/` and `docs/plugin-development.md`; Local REST API: `src/app/core/electron/local-rest-api-router.service.ts` and the `local-rest-api-*-routes.service.ts` file of each feature; URL Scheme Actions: `electron/protocol-handler.ts` and `src/app/features/tasks/util/parse-app-uri-task-action.ts`).

## 1. Sync Server REST API

The Sync Server is an operation-based synchronization service used by the
built-in SuperSync provider. It is not WebDAV. See
[[2.08-Choose-Sync-Backend]] and [[2.09-Configure-Sync-Backend]] for
user-facing sync options.

### Authentication and Authorization

Protected Sync Server endpoints use **JWT Bearer** authentication:
`Authorization: Bearer <token>`. Production account creation and login use
passkeys or emailed magic links; there are no password-based
`POST /api/register` or `POST /api/login` routes. Email-only registration starts
at `POST /api/register/magic-link`.

For the current endpoint purposes, token lifecycle, and security properties, use
the
[authentication authority](https://github.com/super-productivity/super-productivity/blob/master/packages/super-sync-server/docs/authentication.md).
The
[executable routes](https://github.com/super-productivity/super-productivity/blob/master/packages/super-sync-server/src/api.ts)
own exact request and response schemas.

### Synchronization Endpoints

All sync routes require authentication. The stable surface includes operation
upload/download, full-state upload, status, device listing
(`GET /api/sync/devices`), data deletion, restore-point listing, and restore.
`POST /api/sync/snapshot` is an upload endpoint; there is no
`GET /api/sync/snapshot`. Token replacement (`POST /api/replace-token`, in the
account routes rather than under `/api/sync`) invalidates every existing token
for the account and returns a fresh one for the calling client — it backs the
app's "sign out other devices" action; there is no per-device revocation.

Use the
[Sync Server architecture](https://github.com/super-productivity/super-productivity/blob/master/packages/super-sync-server/docs/architecture.md)
for endpoint purposes and executable owners. Exact routes, limits, error codes,
and wire schemas live in
[`sync.routes.ts`](https://github.com/super-productivity/super-productivity/blob/master/packages/super-sync-server/src/sync/sync.routes.ts)
and the
[shared HTTP contract](https://github.com/super-productivity/super-productivity/blob/master/packages/shared-schema/src/supersync-http-contract.ts).

### Agent Task Capture (MCP)

AI assistants can add tasks to your Inbox through the Sync Server's
[MCP](https://modelcontextprotocol.io) endpoint, `<server URL>/mcp`. It is off
by default, both for your account and on the server. It is entirely optional;
Super Productivity works without AI. The server operator must first enable
`CAPTURE_CONNECTOR_ENABLED`.

- **Switch on:** Settings → Sync → SuperSync → expand **AI assistants** →
  **Let AI assistants add tasks**. This section starts collapsed and shows
  whether access is on or off. Expanding it does not enable anything.
  The app creates a key pair, keeps it in your synced settings and registers
  the public key with the server.
- **Claude web (OAuth):** add `<server URL>/mcp` as a custom connector. Select
  **Sign in now** and **Use Claude’s published identity**, without request
  headers. In Super Productivity's AI assistants settings, click **Create
  connection code** and enter it on the consent page opened by Claude. Codes
  work once and expire in 10 minutes. Only enter a code on a page you opened
  from your assistant. After you approve, Claude can refresh its access
  automatically; reconnect after revocation or 90 days without a refresh.
  Use **Refresh connections** in Settings to see the newly connected assistant.
  The server also accepts Claude Code's published OAuth identity.
- **ChatGPT (OAuth):** add `<server URL>/mcp` as a custom MCP connector with
  OAuth, then enter a connection code on the consent page as for Claude.
  Write tools in ChatGPT connectors may require developer mode, depending on
  your plan.
- **Other OAuth clients** need the server operator to add their client ID and
  callback to `CAPTURE_OAUTH_CLIENTS`.
- **Token clients:** expand **Manual tokens for scripts and other clients**,
  enter a name for the assistant and **Create token**. The
  `sp_cap_…` token is shown once and expires after one year. The app then
  shows a Claude Code command with the token filled in; copy it and run it in
  a terminal:

  ```bash
  claude mcp add --transport http super-productivity https://<server>/mcp \
    --header "Authorization: Bearer <token>"
  ```

  Claude Code stores the token in its configuration, and the command stays in
  your shell history; anyone who reads either can add tasks until you revoke
  it. For Claude Code cloud sessions, commit a
  `.mcp.json` to the repository and set `SP_CAPTURE_TOKEN` in the
  environment, not in the file:

  ```json
  {
    "mcpServers": {
      "super-productivity": {
        "type": "http",
        "url": "https://<server>/mcp",
        "headers": { "Authorization": "Bearer ${SP_CAPTURE_TOKEN}" }
      }
    }
  }
  ```

  Clients that accept a custom HTTP header take the same URL and header.
  Each example reads the token from `SP_CAPTURE_TOKEN` (VS Code prompts for
  it) so it stays out of the file:
  - **Codex** (`~/.codex/config.toml`):

    ```toml
    [mcp_servers.super-productivity]
    url = "https://<server>/mcp"
    bearer_token_env_var = "SP_CAPTURE_TOKEN"
    ```

  - **Cursor** (`~/.cursor/mcp.json` or `.cursor/mcp.json`):

    ```json
    {
      "mcpServers": {
        "super-productivity": {
          "url": "https://<server>/mcp",
          "headers": { "Authorization": "Bearer ${env:SP_CAPTURE_TOKEN}" }
        }
      }
    }
    ```

  - **VS Code** (`.vscode/mcp.json`):

    ```json
    {
      "inputs": [
        {
          "type": "promptString",
          "id": "sp-capture-token",
          "description": "Super Productivity capture token",
          "password": true
        }
      ],
      "servers": {
        "super-productivity": {
          "type": "http",
          "url": "https://<server>/mcp",
          "headers": { "Authorization": "Bearer ${input:sp-capture-token}" }
        }
      }
    }
    ```

  - **Gemini CLI** (`~/.gemini/settings.json`):

    ```json
    {
      "mcpServers": {
        "super-productivity": {
          "httpUrl": "https://<server>/mcp",
          "headers": { "Authorization": "Bearer $SP_CAPTURE_TOKEN" }
        }
      }
    }
    ```

  To test a token:

  ```bash
  curl -s https://<server>/mcp -H "Authorization: Bearer $SP_CAPTURE_TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"create_task","arguments":{"title":"Test"}}}'
  ```

- **Tool:** `create_task(title, notes?, dueDate?, dueTime?, repeat?)`. Title up
  to 500 characters, notes up to 8 KiB. `dueDate` (`YYYY-MM-DD`) schedules the
  task for that day; `dueTime` (`HH:MM`, 24-hour) adds a start time and your
  default reminder. `repeat` makes it recurring from `dueDate` (or today):
  `{ "cycle", "every"?, "weekdays"? }` with `cycle` one of `daily`, `weekly`,
  `monthly` or `yearly`, `every` from 1 to 99, and `weekdays` (`"mon"` to
  `"sun"`) for weekly only; monthly and yearly repeat on the start day's date.
  Dates and times are read in the time zone of the device that adds the task;
  app versions from before these options add a one-off, unscheduled task. An
  assistant can only add tasks; it can't read, edit or delete them. Limits:
  30 calls per minute and 200 new tasks per day per token; 200 waiting tasks
  per token and 500 per account. Images in notes arrive as links, so opening
  a task never loads anything from the sender.
- **Arrival:** the server encrypts each task to your public key and holds it.
  Any device with SuperSync and the key adds it to the Inbox after its next
  sync, then the server deletes it. Unclaimed tasks are deleted after 45 days.
- **Revoke:** the settings list each assistant with its waiting tasks.
  **Revoke** keeps tasks it already sent; **Revoke and delete** deletes them.
  **Turn off** revokes every token and deletes all waiting tasks.
  Subsequent MCP calls with a revoked token return HTTP **401 Unauthorized**.
- **Privacy:** the Sync Server and the assistant's provider see the text
  while they handle the request. The Sync Server then stores each task
  encrypted to your key. The private key is part of your synced
  settings, which SuperSync only accepts end-to-end encrypted, so the Sync
  Server cannot read it; your local backups and JSON exports do contain
  it. The key opens only captures held on the SuperSync server. Whoever runs the Sync Server, or anyone with access to
  your sync account, can also add tasks this way or read tasks that
  assistants send later.

## 2. Plugin API

The Plugin API is exposed through a global `PluginAPI` object. Plugins are
privileged extensions, not strongly sandboxed applications: host-side
`plugin.js` code runs in the app renderer, and iframe plugins are same-origin
with the host. See [[2.21-Manage-Plugins]] for the user trust model and
[[3.05-Web-App-vs-Desktop]] for platform differences. Full types and the
development guide live in `packages/plugin-api/src/types.ts` and
`docs/plugin-development.md`.

The types are published on npm as `@super-productivity/plugin-api`, versioned
like the app: version X.Y.Z describes the Plugin API of Super Productivity X.Y.Z.
A plugin's `minSupVersion` is the oldest app version it installs on, so it is
set to the oldest version that has every method the plugin uses. Plain-JavaScript
plugins get autocomplete for the global object with
`/// <reference types="@super-productivity/plugin-api/global" />`. A manifest's
optional `author` is shown on the plugins page.

### Plugin API Categories

**Data — Tasks:**

- `getTasks()`, `getArchivedTasks()`, `getCurrentContextTasks()` — Read tasks.
- `getSelectedTask()` — Read the task selected in the task detail panel, or `null`.
- `getFocusedTask()` — Read the currently focused task row, or `null`. Row focus is transient and is cleared when focus moves elsewhere, including into iframe side panels; use `getSelectedTask()` for persistent side-panel context.
- `addTask(taskData)`, `updateTask(taskId, updates)`, `deleteTask(taskId)` — Create/update/delete. On `addTask`, `parentId` must reference a top-level task; passing a subtask's id is rejected, since the model is only two levels deep. `updateTask` rejects `parentId` and `subTaskIds` — re-parenting is not supported there; use `batchUpdateForProject`, which maintains both sides of the link. It also rejects `wontDoOn`, which is not part of the plugin API. Changing `projectId` moves the task like the UI does: subtasks follow, and for a recurring task the repeat config and every instance (archived ones included) move without a confirmation. Setting `dueDay` adds the task to that Planner day or Today. A scheduled time and its reminder take precedence over `dueDay` and `updateTask` cannot clear a reminder yet, so use it for tasks without a time; the task goes to the end of that day. Derive day strings from `getDayContext().todayStr`.
- `batchUpdateForProject(request)` — Batch create/update/delete/reorder for a project.
- `reorderTasks(taskIds, contextId, contextType)` — Reorder tasks.

**Data — Projects:**

- `getAllProjects()`, `addProject(projectData)`, `updateProject(projectId, updates)`, `deleteProject(projectId)` — Create/update/delete. `deleteProject` deletes the project's tasks with it (backlog and subtasks included), exactly as the UI's own "Delete project" does. Deleting the Inbox is rejected. If the deleted project is the one on screen, the active context falls back to Today.

**Data — Tags:**

- `getAllTags()`, `addTag(tagData)`, `updateTag(tagId, updates)`.

**Data — Simple counters:**

- `setCounter(id, value)`, `getCounter(id)`, `incrementCounter(id, incrementBy)`, `decrementCounter(id, decrementBy)`, `deleteCounter(id)`, `getAllCounters()` — reads/writes by id; `getAllCounters()` returns a plain `{ [id]: number }` value map.
- `getAllSimpleCounters()` — returns the full `SimpleCounter[]` model (title, type, streak config, per-day `countOnDay` history), for plugins that need more than the current value, e.g. rendering streaks or habit history.

**UI:**

- `showSnack(snackCfg)`, `notify(notifyCfg)` — Notifications. `snackCfg.action` (`{ label, onClick }`) adds a button; it works in `plugin.js` only and is dropped for iframe calls, since functions cannot cross `postMessage`.
- `openDialog(dialogCfg)` — Opens a plugin dialog and resolves to the clicked button label, or `undefined` if the dialog is dismissed. The host sanitizes `htmlContent` against an allowlist, keeping semantic HTML, form controls and layout styles while removing scripts, event handlers, unsafe URLs, inline `<svg>`, and styles containing `url(`.
- `showIndexHtmlAsView()` — Shows plugin UI.

**Registration (main plugin context only; not in iframe):**

- `registerHeaderButton(config)`, `registerMenuEntry(config)`, `registerShortcut(config)`, `registerSidePanelButton(config)`, `registerHook(hook, handler)`.
- `unregisterShortcut(shortcutId)` — Removes a shortcut the plugin registered. Registering the same id again replaces the existing entry, so this is only needed when a shortcut goes away for good. The key the user assigned stays in the keyboard settings and applies again if the same id comes back.
- `registerTaskContextMenuEntry(config)` — Adds an action under **Plugin actions** in task context menus. The callback receives `{ taskId }`; `showFor` can limit the action to `TASK` or `SUBTASK`, defaults to both when omitted, and rejects an empty array. `icon` accepts Material icon ligature names only.

**Persistence:**

- `persistDataSynced(dataStr)`, `loadSyncedData()`, `getConfig()` — Plugin-specific storage and config.
- `triggerSync()` — Requests normal sync with the configured provider from `plugin.js` or an iframe. Its `Promise<void>` also resolves on handled errors (`HANDLED_ERROR`) and skipped syncs. Resolution does not confirm successful sync or publication of specific plugin data. Bridge promise rejections propagate to the caller. The iframe's 30-second timeout does not cancel sync that has already started in the host. Feature-detect this method before calling it on older hosts.
- `listSyncedDataKeys(prefix?)` — Lists only the calling plugin's non-empty keyed entries, sorted using JavaScript string order, with optional literal-prefix filtering. The legacy unkeyed entry is excluded. Reads applied application state, not queued or compressing new entries; does not acknowledge disk persistence or remote delivery. Available in `plugin.js` and iframes. Re-read after `persistedDataChanged` and feature-detect on older hosts.

**Day and tracking:**

- `getDayContext()` — `{ todayStr, startOfNextDayDiffMs }`: the logical day as YYYY-MM-DD and the start-of-next-day offset in ms. Re-read on `dayChange`.
- `startTracking(taskId)`, `stopTracking()` — Time tracking. `startTracking` rejects an unknown or done task (it does not reopen it like the play button), and a parent task whose subtasks are all done; for a parent it tracks the first unfinished subtask. The tracked task arrives with `currentTaskChange`.
- Available in `plugin.js` and iframes; feature-detect on older hosts.

**Advanced:**

- `executeNodeScript(request)` — Run Node.js scripts (Electron only, `nodeExecution` permission and user consent).
- `dispatchAction(action)` — Dispatch NgRx actions (allowed subset).
- `downloadFile(filename, data)`, `isWindowFocused()`, `onWindowFocusChange(handler)`.

### Hooks (Events)

Plugins can register handlers for: `taskCreated`, `taskComplete`, `taskUpdate`, `taskDelete`, `currentTaskChange`, `finishDay`, `languageChange`, `persistedDataChanged`, `action`, `anyTaskUpdate`, `projectListUpdate`, `workContextChange`, `dataChanged`, `dayChange`. Payload types are defined in `plugin-api` types (`HookPayloadMap`).

`dataChanged` fires after tasks, projects or tags change from any source, including remote sync, planning and archiving, and when the selected or tracked task changes. Use it to refresh views only: it fires on every device for a synced change, so writing in response repeats the write on each. Bursts are coalesced into one call; while a task is tracked it fires about once a second. The payload is `void`; re-read what you display. `anyTaskUpdate` sees only local actions from a short list.

`dayChange` fires with `{ todayStr }` when the logical day (which honours the start-of-next-day setting) changes while the app runs (at the rollover, or when the start-of-next-day setting moves it).

`persistedDataChanged` fires after the initial boot load on any change to this plugin's persisted data (local write, remote sync, bulk import). The payload is `void`; re-call `loadSyncedData(key?)` for fresh data. No replay-on-register, no ordering guarantee across rapid changes — handlers must be idempotent.

### Plugin Data Types

Core types (Task, Project, Tag, etc.) and batch types (`BatchUpdateRequest`, `BatchUpdateResult`, `BatchOperation`, etc.) are in `packages/plugin-api/src/types.ts`.

### Plugin Manifest

Plugins require `manifest.json`. Use
[`PluginManifest`](https://github.com/super-productivity/super-productivity/blob/master/packages/plugin-api/src/types.ts)
as the current field contract rather than copying its required and optional
fields into the wiki.

A plugin requiring a newer app through `minSupVersion` cannot be installed or
activated, including when reloaded from cache. The error shows the required and
current app versions. Missing or unparseable versions are not blocked by this
compatibility check.

Plugin packages normally include `plugin.js` for host-side behavior. Iframe-only plugins may omit `plugin.js` when
`iFrame: true` is set and `index.html` is included.

### Plugin Permissions

- **nodeExecution:** Required for `executeNodeScript()` (Electron only).
  Built-in and uploaded plugins may request it. The Electron main process shows
  a native consent dialog before granting access and remembers the choice on
  that device until the plugin is disabled; uploaded plugins are labeled as
  unverified third-party code with full machine access.
- Of the declared permissions, the app checks only `nodeExecution`, `http`
  together with `allowedHosts`, and `deleteProject`. The rest are shown in the
  plugin's details but not enforced; see the plugin development guide.

### Iframe API Surface and Trust Boundary

Iframe plugins receive a filtered `window.PluginAPI` object injected into
`index.html`. That object is the supported interface for task/project/tag APIs,
dialogs, notifications, navigation, persistence, registration, counters, and
action dispatch. `executeNodeScript` is proxied through the host bridge when
the desktop app grants `nodeExecution`.

The iframe uses `allow-same-origin`, which is required by the packaged desktop
app. Same-origin iframe code can reach the parent directly, so the filtered
`postMessage` bridge is a convenience and compatibility interface, not a
security boundary. See `docs/plugin-development.md` for the current API surface
and security considerations.

## 3. Local REST API

The Local REST API allows external scripts and tools to interact with a running Super Productivity desktop app. It runs on `http://127.0.0.1:3876` and is disabled by default. Enable it in **Settings → Misc → Enable local REST API**. The switch applies to the current computer only: it is stored locally and not synced, so enabling it on one desktop does not start the API on your other synced devices. The settings panel also shows whether the API is running, or why not (for example, port 3876 already in use).

> **Upgrading from a version where the switch was synced:** the API starts disabled after the update, on every device. Turn it back on in **Settings → Misc** on each computer that should serve it. The existing token stays valid, so scripts need no change.

For development scripts, `SP_FORCE_LOCAL_REST_API=1 npm start` starts the local REST API without changing the persisted user setting. This override only works in `NODE_ENV=DEV`. On a clean profile, set `SP_FORCE_LOCAL_REST_API_TOKEN=<token>` to choose the Bearer token explicitly; otherwise the app generates a temporary development token and prints it to the terminal (stdout, never the exportable app log).

### Prerequisites

- **Electron desktop app only** (not available on web or mobile)
- Must be enabled in settings, unless using the development override
- App must be running with renderer ready

### Authentication

Every request must carry the access token as a Bearer token:

```bash
# Keep the token out of the command line: arguments are visible to every process
# on the machine (`ps`, /proc). Put the header in a file only you can read.
(umask 077; printf 'Authorization: Bearer %s\n' "$SP_TOKEN" > ~/.sp-api-header)

# --noproxy is not optional: curl honours http_proxy/ALL_PROXY even for
# 127.0.0.1, so without it a configured proxy receives your token.
curl --noproxy 127.0.0.1 -H "@$HOME/.sp-api-header" http://127.0.0.1:3876/tasks
```

`-H @file` needs curl 7.55.0 or newer. On older versions put the same line in a
`0600` config file as `header = "Authorization: Bearer <token>"` and pass it with
`--config`. Either way the credential never reaches the process table.

The token is generated automatically when you enable the API, and is shown under
**Settings → Misc → Access Token**, where you can also regenerate it. Regenerating
invalidates the previous token immediately.

A missing, malformed, or wrong token returns `401` with the `UNAUTHORIZED` error code and a
`WWW-Authenticate: Bearer` header. `GET /health` is the only exception and stays
unauthenticated so tooling can probe liveness.

> The examples below omit the `Authorization` header for brevity — every one of them needs
> it except `/health`.

### What the Token Does and Does Not Protect

The token is stored per device in a `0600` file inside the
[[3.06-User-Data]] folder and is never synced or exported. It closes the
case where **another account on the machine**, or a sandboxed process that cannot read
that file, talks to the API: before, every local process could read and modify all of
your tasks.

Two limitations are deliberate, and worth knowing before you enable the API:

- **Any process running as you can read the token file**, and therefore your tasks. On a
  single-user desktop that is most processes. File permissions are a boundary between
  accounts, not between programs you run.
- **The API does not authenticate itself to clients.** The port is fixed and unprotected,
  so a process that binds `127.0.0.1:3876` while Super Productivity is _not_ listening —
  before the app starts, or while the API is switched off — receives the `Authorization`
  header of the next client that connects, and can release the port and reuse that token
  afterwards. `GET /health` is unauthenticated, so an impostor can also answer a liveness
  probe convincingly. Closing this would require the server to prove its identity over a
  protected transport; retrying or moving the port does not help, because the impostor
  binds it while the app is down.

So: enable the API on a machine where you trust every account that can bind a loopback
port, and treat the token as a credential — regenerate it if it may have been exposed.

### Base URL

```text
http://127.0.0.1:3876
```

### Response Format

All responses are JSON with a consistent envelope:

```typescript
// Success
{ "ok": true, "data": <response data> }

// Error
{ "ok": false, "error": { "code": "<ERROR_CODE>", "message": "<description>" } }
```

### Task Endpoints

| Method | Path                 | Description                        |
| ------ | -------------------- | ---------------------------------- |
| GET    | `/tasks`             | List tasks (with optional filters) |
| GET    | `/tasks/:id`         | Get task by ID                     |
| POST   | `/tasks`             | Create task                        |
| PATCH  | `/tasks/:id`         | Update task                        |
| DELETE | `/tasks/:id`         | Delete task                        |
| POST   | `/tasks/:id/start`   | Start task (set as current)        |
| POST   | `/tasks/:id/time`    | Add time spent on a given day      |
| PUT    | `/tasks/:id/time`    | Set or remove time spent on a day  |
| POST   | `/tasks/:id/archive` | Archive task                       |
| POST   | `/tasks/:id/restore` | Restore archived task              |

**GET /tasks/:id** returns the task. `include` asks for optional fields: a comma-separated list (`?include=issueUrl`) or the parameter repeated; values are case-sensitive and unknown ones are ignored. The only optional field so far is `issueUrl`: for a task linked to an issue whose provider can build a link to it, the link as a string. It is omitted when there is no issue, no link, or the lookup fails or takes longer than about 3 seconds; it never turns the request into an error. It is opt-in because some providers fetch the issue over the network to build the link. `GET /tasks` does not include `issueUrl`.

`?source=active` answers `404 TASK_NOT_FOUND` for a task of an archived project, matching what `GET /tasks` lists by default; without it the task is returned wherever it lives in the store.

**POST /tasks/:id/archive** and **POST /tasks/:id/restore** answer `200` once the move is complete: an archived task is no longer listed as active, and a restored task is no longer listed with `?source=archived`.

**GET /tasks Query Parameters:**

| Parameter     | Type    | Description                                                 |
| ------------- | ------- | ----------------------------------------------------------- |
| `query`       | string  | Filter by title (case-insensitive, contains)                |
| `projectId`   | string  | Filter by project ID                                        |
| `tagId`       | string  | Filter by tag ID. Use `TODAY` for tasks scheduled for today |
| `includeDone` | boolean | Include completed tasks (default: false)                    |
| `source`      | string  | `"active"` \| `"archived"` \| `"all"` (default: `"active"`) |

`"active"` leaves out tasks of archived projects, as the app itself does; use `"all"` to include them.

**Examples:**

```bash
# List all active tasks
curl http://127.0.0.1:3876/tasks

# List archived tasks
curl "http://127.0.0.1:3876/tasks?source=archived"

# Search tasks containing "meeting"
curl "http://127.0.0.1:3876/tasks?query=meeting"

# List tasks scheduled for today
curl "http://127.0.0.1:3876/tasks?tagId=TODAY"

# Create a task
curl -X POST http://127.0.0.1:3876/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "Buy groceries", "projectId": "INBOX_PROJECT"}'

# Create a subtask (parent must be a top-level task; the subtask inherits
# the parent's projectId and cannot have its own tags)
curl -X POST http://127.0.0.1:3876/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "milk", "parentId": "PARENT_TASK_ID"}'

# Update a task
curl -X PATCH http://127.0.0.1:3876/tasks/task-id \
  -H "Content-Type: application/json" \
  -d '{"title": "Updated title"}'

# Log 1.5 hours on a past day
curl -X POST http://127.0.0.1:3876/tasks/task-id/time \
  -H "Content-Type: application/json" \
  -d '{"date": "2026-05-10", "duration": 5400000}'

# Archive a task
curl -X POST http://127.0.0.1:3876/tasks/task-id/archive
```

**POST /tasks body fields:**

| Field                | Notes                                                                                                                                                                                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title` (required)   | Non-empty string                                                                                                                                                                                                                                                                                  |
| `parentId`           | Create the task as a subtask of this top-level task. Returns 404 if parent missing, 400 if parent is itself a subtask. The new subtask inherits the parent's `projectId` and never has its own tags — supplying `projectId` or `tagIds` together with `parentId` returns 400 `UNSUPPORTED_FIELD`. |
| `subTaskIds`         | Not supported on create — returns 400 `UNSUPPORTED_FIELD`. Create the parent first, then create each child with `parentId`.                                                                                                                                                                       |
| other allowed fields | `notes`, `isDone`, `timeEstimate`, `timeSpent`, `projectId`, `tagIds`, `dueDay`, `dueWithTime`, `deadlineDay`, `deadlineWithTime`, `deadlineRemindAt`, `priority`; deprecated alias: `plannedAt` maps to `dueWithTime` when `dueWithTime` is not supplied.                                        |

**Short Syntax:** a title sent to `POST /tasks`, or a `PATCH /tasks/:id` whose only change besides deadline fields is the title, is parsed like a typed task, according to the user's Short Syntax settings (see [[3.04-Short-Syntax]]) — e.g. `#tag`, `+Project` or `30m` can be taken out of the title and applied. Send `"isIgnoreShortSyntax": true` in the body to store the title literally instead, which is useful when the title comes from another app. A non-boolean value returns 400 `INVALID_INPUT`. Versions before this flag existed ignore it and parse the title.

**PATCH /tasks/:id — restricted fields:**

`parentId` and `subTaskIds` cannot be set via `PATCH` (returns 400 `UNSUPPORTED_FIELD`). Re-parenting an existing task is not supported by this API; delete and recreate the task instead.

Changing `projectId` on a top-level task moves it like the UI does: its subtasks follow, and for a recurring task the repeat config and every instance (archived ones included) move without a confirmation. The destination must be an existing active project; missing or archived destinations return 404 `PROJECT_NOT_FOUND`. A subtask's `projectId` is inherited from its parent and cannot be changed directly (400 `UNSUPPORTED_FIELD`); echoing its unchanged inherited value is accepted for GET-to-PATCH round trips. A project move can be combined with other writable fields in the same PATCH request.

`isDone: true` on a task that is already done is ignored, so a round trip keeps its completion date and a task finished as won't do stays won't do.

**Priority:** `priority` accepts `1` (Low), `2` (Medium) or `3` (High), the numbers the UI writes; `null` clears it. Other values, including the legacy strings `"low"`, `"medium"` and `"high"` that `GET` can still return for older data, return 400 `INVALID_INPUT`. On a recurring task this changes only that instance, like the task's context menu; the priority of future instances lives in the repeat config.

`plannedAt` is accepted as a deprecated alias for `dueWithTime` on PATCH; when both are supplied, `dueWithTime` takes precedence. `plannedAt: null` clears `dueWithTime`.

**Scheduled time:** the task reminder follows `dueWithTime`. Moving the time moves the reminder and keeps its offset, `null` dismisses it, and a task that gets a time for the first time gets the default task reminder from the reminder settings. A task that was scheduled without a reminder stays without one.

**Deadlines:** `deadlineDay` accepts a valid calendar `YYYY-MM-DD` date. `deadlineWithTime` and `deadlineRemindAt` accept positive Unix timestamps in milliseconds. The deadline types are mutually exclusive; changing a deadline clears its existing `deadlineRemindAt` unless a new reminder is supplied in the same request. Re-sending the current deadline value, or nulling only its inactive field, is a no-op. A task with an existing deadline can update `deadlineRemindAt` alone; an explicit `null` clears just the reminder and never re-plans the deadline. Any request that sets a deadline value or a non-null reminder dispatches the same `setDeadline` action as the deadline dialog, so it also re-applies the automatic Today planning for the deadline: a deadline that is today can rewrite `dueDay` to today and clear `dueWithTime` plus `remindAt`, exactly as saving the dialog with only the reminder changed would. A request that changes nothing (a re-sent deadline, or a null on an inactive field) dispatches nothing. Supplying both deadline fields as non-null in one request returns 400 `INVALID_INPUT`.

Clear all deadline fields with nulls:

```bash
curl -X PATCH http://127.0.0.1:3876/tasks/task-id \
  -H "Content-Type: application/json" \
  -d '{"deadlineDay": null, "deadlineWithTime": null}'
```

Set a day deadline and its reminder together:

```bash
curl -X PATCH http://127.0.0.1:3876/tasks/task-id \
  -H "Content-Type: application/json" \
  -d '{"deadlineDay": "2026-08-15", "deadlineRemindAt": 1786777200000}'
```

**POST /tasks/:id/time** adds time spent to a task on one day, the same way time tracked in the app does: it adds to the task's `timeSpentOnDay` for `date` and its total `timeSpent`, rolls the time up to a parent task, and syncs. Use it to log time for a past day; patching `timeSpent` does not change `timeSpentOnDay` and is overwritten the next time the total is recalculated. The response is the updated task.

| Field                 | Notes                                                                               |
| --------------------- | ----------------------------------------------------------------------------------- |
| `date` (required)     | The day to log the time on, as a valid calendar `YYYY-MM-DD` date, today or earlier |
| `duration` (required) | Time to add, as a positive integer of milliseconds, at most 24 hours                |

"Today" is the app's logical day, so it follows the start-of-next-day setting. Logging time on a past day changes only the task's time: it does not change that day's work start and end, and it does not add the task to today. A day can hold at most 24 hours per task, counting the time already logged on it. A parent task's time is the sum of its subtasks', so log time on a subtask; a task that has subtasks returns 400 `INVALID_INPUT`.

A field other than `date` and `duration` returns 400 `UNSUPPORTED_FIELD`; an invalid body, a future date or more than 24 hours on the day returns 400 `INVALID_INPUT`; an unknown or archived task returns 404 `TASK_NOT_FOUND`.

**PUT /tasks/:id/time** sets the day's total instead of adding to it. It accepts the same required `date` and `duration` fields and the same restrictions as POST, except that `duration` can be zero to remove that day's entry. Other days are preserved, and the task's total and its parent's total are recalculated through the same path as the time edit dialog. The response is the updated task.

Use PUT to correct or remove logged time. Repeating the same value without an intervening change dispatches nothing. A running timer keeps running, so subsequent tracking can increase today's value again.

```bash
# Set the day's total to one hour
curl -X PUT http://127.0.0.1:3876/tasks/task-id/time \
  -H "Content-Type: application/json" \
  -d '{"date": "2026-05-10", "duration": 3600000}'

# Remove the day's logged time
curl -X PUT http://127.0.0.1:3876/tasks/task-id/time \
  -H "Content-Type: application/json" \
  -d '{"date": "2026-05-10", "duration": 0}'
```

### Focus State Endpoint

| Method | Path     | Description                                               |
| ------ | -------- | --------------------------------------------------------- |
| GET    | `/focus` | Get the current read-only Focus Mode timer state and mode |

`GET /focus` reports the authoritative Focus Mode state used by the desktop app. It
does not expose task content and does not add controls for starting, pausing,
resuming, skipping, or cancelling a focus session.

```bash
curl http://127.0.0.1:3876/focus
```

**Response data:**

```typescript
{
  mode: 'Flowtime' | 'Pomodoro' | 'Countdown';
  cycle: number;
  isSessionDone: boolean;
  timer: null | {
    purpose: 'work' | 'break';
    status: 'running' | 'paused' | 'done';
    isOvertime: boolean;
    isLongBreak: boolean;
    elapsedMs: number;
    remainingMs: number;
    durationMs: number;
  };
}
```

`timer` is `null` when no work or break timer exists. A completed work session is
represented by `timer: null` and `isSessionDone: true`; a completed break retains its
break timer with `status: 'done'`. Other active timer states are `running` or `paused`.
`isSessionDone` mirrors the current Focus Mode screen, so it can remain true after the
overlay is dismissed until another focus action changes the screen.
`isOvertime` is independent from `status`, so it remains true when an overtime work
session is paused. Flowtime timers have no countdown duration, so their `remainingMs`
is zero while their status remains `running` or `paused`.

`cycle` is the 1-based counter used by Pomodoro. Only completing a Pomodoro work
session advances it, so it is already advanced during that session's following break.
Switching to Flowtime or Countdown retains the current value, but those modes do not
advance it. Focus Mode state is not persisted, so the cycle resets to `1` when the app
restarts and when the user explicitly resets the Pomodoro cycle count.

### Repeat Config Endpoints

A repeat config makes a task recur. It is created from an existing task, as the "Repeat" option in the task's schedule dialog does, and holds the schedule plus the title, notes, tags, estimate and priority the next instances get.

| Method | Path                    | Description                 |
| ------ | ----------------------- | --------------------------- |
| GET    | `/task-repeat-cfgs`     | List repeat configs         |
| GET    | `/task-repeat-cfgs/:id` | Get repeat config by ID     |
| POST   | `/task-repeat-cfgs`     | Make a task repeat          |
| PATCH  | `/task-repeat-cfgs/:id` | Change schedule, pause      |
| DELETE | `/task-repeat-cfgs/:id` | Stop repeating (delete cfg) |

**GET /task-repeat-cfgs Query Parameters:**

| Parameter   | Type   | Description                               |
| ----------- | ------ | ----------------------------------------- |
| `projectId` | string | Only list the repeat configs of a project |

Paused configs are included in the list (`isPaused: true`).

**POST /task-repeat-cfgs and PATCH /task-repeat-cfgs/:id body fields:**

| Field                 | Type    | Notes                                                                                                                                                                                                |
| --------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `taskId`              | string  | Required on create, not accepted on update. An active top-level task that is not linked to an issue and does not repeat yet                                                                          |
| `quickSetting`        | string  | `DAILY` (default on create), `MONDAY_TO_FRIDAY`, `WEEKLY_CURRENT_WEEKDAY`, `MONTHLY_CURRENT_DATE`, `MONTHLY_FIRST_DAY`, `MONTHLY_LAST_DAY`, `MONTHLY_NTH_WEEKDAY`, `YEARLY_CURRENT_DATE` or `CUSTOM` |
| `startDate`           | string  | `YYYY-MM-DD`, from `1000-01-01`. Defaults to the task's day, or today. On create, it must not be before that day                                                                                     |
| `repeatCycle`         | string  | `CUSTOM` only: `DAILY`, `WEEKLY`, `MONTHLY` or `YEARLY`                                                                                                                                              |
| `repeatEvery`         | number  | `CUSTOM` only: an integer from 1 to 1000                                                                                                                                                             |
| `monday` ... `sunday` | boolean | `CUSTOM` only: the weekdays of a weekly schedule; a weekly custom schedule needs at least one                                                                                                        |
| `isPaused`            | boolean | Pause or resume creating new instances (default on create: `false`)                                                                                                                                  |
| `skipOverdue`         | boolean | Don't let overdue instances pile up. Default on create: `true` for an everyday schedule, `false` otherwise                                                                                           |

As in the repeat dialog, a preset `quickSetting` derives the cycle and weekdays from the start date (for example, `WEEKLY_CURRENT_WEEKDAY` repeats on the start date's weekday), and some presets move the start date (`MONTHLY_FIRST_DAY` starts on the next 1st; a move past `9999-12-31` returns 400 `INVALID_INPUT`). The schedule is changed as a whole: a `PATCH` with any of `quickSetting`, `startDate`, `repeatCycle`, `repeatEvery` or a weekday must include `quickSetting`. Only changed fields are saved. As when saving the dialog, a schedule change moves the newest unfinished instance to the next matching day; existing instances keep their title, notes and other content.

The title, notes, tags, estimate, priority and time are copied from the task on create. A config with a time gets the default task reminder from the reminder settings, as in the dialog. Any other field returns 400 `UNSUPPORTED_FIELD`; a wrong value type or an invalid schedule returns 400 `INVALID_INPUT`. An unknown task returns 404 `TASK_NOT_FOUND`, an unknown repeat config 404 `REPEAT_CFG_NOT_FOUND`. `POST` returns 201 with the created repeat config, `PATCH` returns 200 with the updated one, and `DELETE` returns 200 with `{ "deleted": true, "id": "..." }`. Deleting a repeat config keeps its tasks; they just no longer repeat.

**Examples:**

```bash
# Repeat a task every weekday
curl -X POST http://127.0.0.1:3876/task-repeat-cfgs \
  -H "Content-Type: application/json" \
  -d '{"taskId": "task-id", "quickSetting": "MONDAY_TO_FRIDAY"}'

# Repeat a task every second week on Tuesday and Thursday
curl -X POST http://127.0.0.1:3876/task-repeat-cfgs \
  -H "Content-Type: application/json" \
  -d '{"taskId": "task-id", "quickSetting": "CUSTOM", "repeatCycle": "WEEKLY", "repeatEvery": 2, "monday": false, "tuesday": true, "wednesday": false, "thursday": true, "friday": false}'

# Pause it
curl -X PATCH http://127.0.0.1:3876/task-repeat-cfgs/repeat-cfg-id \
  -H "Content-Type: application/json" \
  -d '{"isPaused": true}'

# Stop repeating
curl -X DELETE http://127.0.0.1:3876/task-repeat-cfgs/repeat-cfg-id
```

### Assistant Access (MCP)

The desktop app can also serve AI assistants through the [Model Context Protocol](https://modelcontextprotocol.io) (MCP) at `http://127.0.0.1:3876/mcp`. It shares the Local REST API's listener but has its own switch, its own access key and its own permissions; neither credential works on the other endpoint. Enable it in **Settings → Misc → Enable assistant access**. Like the REST API switch, it applies to the current computer only and is not synced. Setup recipes for more clients and what stays local: [[2.23-Connect-an-AI-Assistant]].

- **Access key:** generated in the settings panel and shown once; only a hash is stored. Send it as `Authorization: Bearer <key>`. Replacing the key disconnects clients that use the old one immediately.
- **Permissions** (all off by default):
  - _Read tasks_ — task summaries (title, done state, project and tag ids, due and deadline fields, estimate and time spent), plus project and tag names. Only active tasks; the archive is never exposed.
  - _Also read task notes_ — notes via `get_task`, capped at 8 KB. Requires _Read tasks_.
  - _Add new tasks to the Inbox_ — `create_task` only. The title and notes are stored exactly as sent: no short syntax is parsed and nothing from the currently open view (project, tag, Today) is applied. Optional `dueDate`, `dueTime` and `repeat` schedule the task, as in the SuperSync `create_task` above. Otherwise the task behaves like one added to the Inbox by hand: default estimates apply, and an issue integration set to auto-create issues for Inbox tasks will do so. It reveals no existing data.
- **Tools:** `get_status` (always), `list_tasks`, `get_task`, `list_projects`, `list_tags` (_Read tasks_), `create_task` (_Add new tasks_). A client only sees the tools its permissions allow.
- **Protocol:** Streamable HTTP, stateless, JSON responses, protocol versions `2025-03-26` to `2025-11-25`. Clients that speak the newer `2026-07-28` revision fall back automatically. Requests with any `Origin` header are refused, so browsers cannot reach it.
- **Claude Code:** `claude mcp add --scope user --transport http super-productivity http://127.0.0.1:3876/mcp --header "Authorization: Bearer <key>"`
- **Codex:** add the following to `~/.codex/config.toml`, replacing `<key>` with the generated assistant access key, then restart the client. The generic JSON shown in the settings panel is not a `config.toml` entry. See [Codex MCP configuration](https://developers.openai.com/codex/mcp).

  ```toml
  [mcp_servers.super-productivity]
  url = "http://127.0.0.1:3876/mcp"
  http_headers = { Authorization = "Bearer <key>" }
  ```

- **Claude Desktop (Windows, macOS):** Claude Desktop only launches local servers over stdio, and its remote connectors run in the cloud and cannot reach `127.0.0.1`. Install the Super Productivity extension instead: download [`super-productivity.mcpb`](https://github.com/super-productivity/super-productivity/releases/latest/download/super-productivity.mcpb) from the latest release (the settings panel links to it), open it with Claude Desktop and paste the access key when asked. The extension only relays messages to this endpoint, so the app's permissions apply. It does not work with the Mac App Store build, which cannot open the local port yet.
- **Other clients:** any MCP client that supports HTTP servers with a custom `Authorization` header.
- **Privacy:** the assistant sends what it reads to its model provider, which may be a cloud service. Nothing is sent by Super Productivity itself.
- **Capture results:** `create_task` answers `created` only after the task was saved locally. If the outcome is uncertain (for example, a timeout) it says so instead of claiming failure; retrying can then create a duplicate.

## 4. URL Scheme Actions

Two kinds of action are reachable through the app's existing custom URL scheme. **Task actions** — **add a task** and **complete a task** (matched by title) — do their work without opening the app UI first. **UI actions** — open the add-task bar, or jump to Today or the Inbox — only navigate; they never read or write task data.

This is intended for external automation — most notably an iOS Shortcut's "Open URLs" action (which also makes the actions reachable via Siri, see below) and Android automation apps — but works anywhere a URL can be opened. On iOS and Android the UI actions are additionally wired to the launcher shortcuts you get by long-pressing the app icon (see below).

Not available in the web (browser) build, which has no URL scheme registration.

### Platforms and Schemes

| Platform            | Scheme                          | Example                                                     |
| ------------------- | ------------------------------- | ----------------------------------------------------------- |
| iOS (Capacitor)     | `com.super-productivity.app://` | `com.super-productivity.app://create-task?title=Buy%20milk` |
| Android (Capacitor) | `com.super-productivity.app://` | `com.super-productivity.app://create-task?title=Buy%20milk` |
| Desktop (Electron)  | `superproductivity://`          | `superproductivity://create-task?title=Buy%20milk`          |

Both schemes are already registered for other purposes (OAuth callbacks on mobile; global-shortcut and window-visibility actions on desktop) — these are two more recognized actions on the same schemes, not a new registration.

Use the action names in lowercase. On Android the OS matches the declared hosts case-sensitively, so `://Create-Task` won't resolve at all; iOS and desktop register the whole scheme and lowercase the action in the app, but lowercase is the only form that works everywhere.

### Task Actions

**Add a task** — action `create-task` on all platforms (desktop also accepts the title as a path segment, `create-task/<title>`, matching the pre-existing desktop action shipped since v14.2.4 — whose title handling this changes, see the Short Syntax note below). Not `add-task`: desktop's `add-task` protocol action already exists and does something unrelated (opens the quick-add-task input bar).

| Query parameter | Required | Description                                                                                                                                   |
| --------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`         | Yes      | The new task's title. Surrounding whitespace is trimmed; whitespace-only is rejected (no task is added). Max 300 characters (after trimming). |
| `notes`         | No       | Task notes. Max 100,000 characters.                                                                                                           |
| `projectId`     | No       | Target project ID. The action fails with an error (no task added) if it doesn't match an existing project.                                    |

**Short Syntax is _not_ parsed** (see [[3.04-Short-Syntax]]): tokens like `+Project`, `#tag`, or `@date` in the title are stored literally rather than creating/assigning a project, tags, or a due date (surrounding whitespace is still trimmed). A URL is untrusted external content, so — as with the email-drop import — it can't silently create tags/projects or override an explicit `projectId`. Use the `projectId` parameter to set the project.

> **Behavior change:** the pre-existing desktop `create-task` action (shipped since v14.2.4) previously parsed Short Syntax on the title, like a manually typed task. As of this change the title is stored literally on all platforms. Pass `projectId` for the project; `+`/`#`/`@` tokens are no longer interpreted.

Without an explicit `projectId`, the task is added to whichever project/tag/context is currently active in the app — which on a cold launch is whatever was last open, not necessarily the Inbox. Pass `projectId` for deterministic placement.

**Complete a task** — action `complete-task` on all platforms.

| Query parameter | Required | Description                                                                                                                                                                                        |
| --------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`         | Yes      | Matched (trimmed, case-insensitive) against non-subtask, non-done tasks in active (non-archived) projects. Only a lookup needle, never stored, so it is not subject to the create-task length cap. |

An exact case-insensitive title match is preferred; if there is none, a case-insensitive substring match is used, but only when exactly one task matches. If no task matches, or more than one substring match is equally plausible, the action fails with an error rather than guessing.

**Examples:**

```text
com.super-productivity.app://create-task?title=Buy%20milk&notes=2%25%20fat&projectId=proj-1
com.super-productivity.app://complete-task?title=Buy%20milk

superproductivity://create-task?title=Buy%20milk
superproductivity://complete-task?title=Buy%20milk
```

### UI Actions

These take no parameters and change no data — each one opens something the user could have reached by tapping, so there is no success or error snack: the app landing where you asked _is_ the feedback.

| Action     | What it does                                                              |
| ---------- | ------------------------------------------------------------------------- |
| `add-task` | Opens the quick-add-task input bar in whichever context is currently open |
| `today`    | Opens the Today view                                                      |
| `inbox`    | Opens the Inbox project                                                   |

`add-task` is deliberately _not_ `create-task`: it only opens the input bar and waits for you, while `create-task` adds a task outright. `add-task` has existed as a desktop protocol action since before this and behaves identically there.

All three work in the desktop and mobile apps; they are also what the iOS Home Screen quick actions, the Android app shortcuts and the desktop dock menu and jump list below are built on. On desktop they are `superproductivity://` protocol actions (`superproductivity://today`). To reach them from elsewhere on Android, open the URLs from an automation app (e.g. Tasker, Automate).

**Examples:**

```text
com.super-productivity.app://add-task
com.super-productivity.app://today
```

### iOS Home Screen Quick Actions

Long-pressing the app icon on the iOS Home Screen shows three shortcuts — **New Task**, **Today** and **Inbox** — which open the app straight into the matching UI action above. They work on a cold start too: the action is queued until the app has finished loading its data, then runs.

The menu is static, so it is there immediately after installing and never changes. Two consequences worth knowing:

- The labels are always English, whatever language the app itself is set to. iOS reads static quick-action titles from the app bundle, not from the app's own translations.
- Only Today and the Inbox are offered, not Planner, Schedule, Boards or Habits. Because the menu cannot change per user, it would otherwise show entries for features you may have switched off under Settings → App Features — and new installs start with several of them off. Today and the Inbox are always present, so the menu is always accurate.

### Android App Shortcuts

On Android 7.1 and later, long-pressing the app icon in the launcher shows the same three shortcuts — **New task**, **Today** and **Inbox** — and they behave the same way: each opens the matching UI action above, from a cold start or with the app already running. If the app is already open, it is brought to the front as it was; it is not restarted. Most launchers also let you drag a shortcut out of the menu onto the home screen as its own icon.

As on iOS, the set is fixed to the three always-present entries. The labels are English only for now: Android reads them from the app's native text, which, like the home screen widget's, is not translated yet.

### Desktop Dock Menu and Jump List

On macOS, right-clicking the app's Dock icon shows the same three entries — **New task**, **Today** and **Inbox** — while the app is running. On Windows (installer version), they are in the jump list you get by right-clicking the taskbar icon. Each one opens the matching UI action above. The labels are English only, like the tray menu. Linux, and the portable and Microsoft Store builds on Windows, have no such menu; bind the `superproductivity://` URLs instead (see [[3.03-Keyboard-Shortcuts]]).

### Triggering via Voice Assistants

- **Siri (iOS):** create a Shortcut in the Apple Shortcuts app — "Ask for Input" (text) followed by "Open URLs" with `com.super-productivity.app://create-task?title=` and the input appended — then invoke it by name: "Hey Siri, \<shortcut name\>". Siri dictates the title, the URL opens the app, and the task is added. Query parameter values must be URL-encoded; Shortcuts' "URL Encode" action handles titles with spaces or special characters.
- **Google Assistant / Gemini (Android):** no direct voice integration exists for this app — Google removed third-party notes/lists Assistant integration in 2023, and Gemini's successor mechanism (AppFunctions) has no public third-party integration path yet (as of 2026-08). Android automation apps (e.g. Tasker, Automate) can open these URLs to create tasks, open the add-task bar, or jump to Today or the Inbox from their own triggers.

### Behavior Notes

- For the task actions, all platforms show a snack notification on success (task added/completed) or failure (no matching/ambiguous task, unknown project) — there is no other feedback channel for a URL triggered from outside the app. The UI actions show none, because the navigation itself is visible.
- The UI actions never create, modify or complete anything, so they are safe to trigger repeatedly.
- An action received during a cold launch (app not already running) is queued until the app's own data has finished loading, so it never races initial hydration. This applies to both kinds of action.
- On Android, opening the URL brings the app to the foreground (the action is handled by the main activity); there is no background execution.
- Not available in the web (browser) build — see [[3.05-Web-App-vs-Desktop]].

## 5. Versioning and Compatibility

### Schema Versioning (Sync)

Operations and snapshots carry `schemaVersion`. The current and minimum
supported versions, together with the compatibility policy, are defined in
`packages/shared-schema/src/schema-version.ts`. Newer schemas are blocked
rather than interpreted using a copied "version skip" allowance.

### Vector Clocks

Sync uses bounded vector clocks for conflict resolution. The canonical size and
pruning rules are in `packages/sync-core/src/vector-clock.ts`; server-side input
sanitization is in `packages/super-sync-server/src/sync/sync.types.ts`. The
server may temporarily accept a larger clock during conflict resolution before
pruning it, so an input-validation limit is not the stored clock size.

### API Validation (Sync Server)

- Operation IDs: 1–255 characters. Client IDs: alphanumeric, underscore, hyphen; max 255.
- Entity types: 1–255 characters. Schema version: 1–100.
- Payload validation by op type (CRT, UPD, DEL, MOV, BATCH, SYNC_IMPORT, etc.); see `validatePayload` in `sync.types.ts`.

## General Notes

- **Sync Server:** Production-oriented (JWT, rate limiting, CORS, Helmet). Multi-instance deployment has limitations (e.g. passkey challenge storage in memory; snapshot generation locks); single-instance is the typical deployment.
- **Plugin API:** Privileged and not strongly sandboxed; iframe, web, and
  Electron have different capabilities. See [[2.21-Manage-Plugins]],
  [[3.05-Web-App-vs-Desktop]], and the repository plugin guide.
- **Local REST API:** Desktop-only, localhost-bound, and protected by a Bearer access token on every request except `/health`. For automation and scripting. See [[3.05-Web-App-vs-Desktop]] for platform differences.
- **URL Scheme Actions:** iOS and Android (Capacitor) and desktop (Electron), not the web build. No authentication — any process able to open a URL on the device can trigger it, same trust model as the existing OAuth-callback/global-shortcut actions on the same schemes.
- **Further documentation:** Sync Server README and auth docs in `packages/super-sync-server/`; Plugin API and examples in `packages/plugin-api/`, `docs/plugin-development.md`, and example plugins under `packages/plugin-dev/`; Local REST API types in `electron/shared-with-frontend/local-rest-api.model.ts`.
