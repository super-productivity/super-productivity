# Deploy on Coolify

How to run the Super Productivity web app and your own SuperSync server on [Coolify](https://coolify.io), as a single resource with automatic HTTPS.

For a plain Docker host, see [[2.13-Run-with-Docker]] instead.

## What you get

One Coolify resource, three containers:

| Container   | What it is                                                               |
| ----------- | ------------------------------------------------------------------------ |
| `app`       | The web app. Your tasks live in each browser's own storage.              |
| `supersync` | The sync backend. Its own web page is only the login and account screen. |
| `postgres`  | The database behind `supersync`.                                         |

The app is usable on its own. `supersync` is what makes your tasks follow you to another browser or device, and it stays unused until you turn it on.

## Before you start

You need a Coolify server with a domain pointed at it, and a GitHub account — Coolify deploys from a repository.

## Steps

### 1. Create the resource

In Coolify, create a new resource of type **Docker Compose** and connect your GitHub account.

Point it at the `super-productivity/super-productivity` repository with **Docker Compose File** set to:

```txt
packages/super-sync-server/docker-compose.coolify.yml
```

### 2. Choose the services

Select all three services: `supersync`, `postgres`, and `app`.

Coolify generates and stores the database password and the JWT signing secret for you. You do not create them and you should not overwrite them.

### 3. Assign two domains

Assign a domain to `supersync`, for example `sync.example.com`, and a different one to `app`, for example `sp.example.com`. Coolify requests the TLS certificate for both.

The sync server derives its own public URL and passkey settings from the domain you assign here, so do not set those values by hand.

### 4. Set the app's origin

Set this environment variable on the resource:

```txt
CORS_ORIGINS=https://sp.example.com
```

The sync server only accepts browser requests from the origins listed here, and it ships with just our own hosted app allowed. Without this the app loads normally and then every save fails with a network error.

### 5. Deploy

Deploy the resource. Coolify creates the containers, runs the database migrations, and brings the services up in order, waiting for the database to become healthy first.

When it finishes, open your app domain and you have a working Super Productivity in the browser.

### 6. Turn on sync (optional)

Open the sync server's domain in a browser and create your account there.

Then in the app, go to **Settings → Sync → SuperSync**, enter the sync server's URL, and log in with the same account. Repeat on any other browser or device.

Until you do this, nothing is uploaded and the servers stay empty.

## Optional settings

Everything else is documented in `env.example` next to the compose file, with its default. These three are the ones worth setting deliberately:

| Variable                                                                                                                     | Purpose                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `ALLOWED_EMAILS`                                                                                                             | Restrict who may register, as exact addresses and/or `*@domain.com`.                                                  |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`                                               | Sending the verification, magic-link, and password-recovery emails. Without these, email-based signup cannot deliver. |
| `PRIVACY_CONTACT_NAME`, `PRIVACY_ADDRESS_STREET`, `PRIVACY_ADDRESS_CITY`, `PRIVACY_ADDRESS_COUNTRY`, `PRIVACY_CONTACT_EMAIL` | Identify yourself as the data controller so a privacy policy is published.                                            |

The five `PRIVACY_` contact values are all-or-nothing: set all of them or none. Setting some but not all is rejected, because a policy naming the wrong controller is worse than no policy.

## Upgrading

Redeploy the resource. Coolify pulls the current images and re-applies the migrations.

To pin a fixed revision instead of tracking the latest build, set `SUPERSYNC_IMAGE` to a `master-<sha>` tag. The server image has no release tags, so `latest` follows the current `master` branch.

## Things worth knowing

### The generated secrets are effectively permanent

Coolify keeps the database password and JWT secret, so they survive ordinary redeploys. Do not edit or regenerate them afterwards:

- **Changing the database password** leaves the database running and holding your data while the server crash-loops with `password authentication failed`. To change it, delete the database volume and redeploy — that discards all synced data.
- **Changing the JWT secret** invalidates every issued session token, logging all devices out.

Copy both values somewhere safe after the first successful deploy.

### Memory limits

The default caps are `768m` for the server and `1536m` for the database, which is generous for a small instance. Lower both if your host is small — `SUPERSYNC_MEM_LIMIT`, `POSTGRES_MEM_LIMIT`, and `POSTGRES_EFFECTIVE_CACHE_SIZE`, where the cache should be roughly the limit minus 384 MB. Do not raise the database limit to or above your host's total RAM: the host, not the container, then decides what gets killed when memory runs out.

### Back up the database

The database volume holds everything that was synced. See the SuperSync server's `docs/backup-and-recovery.md` in the repository for how to dump and restore it. A Coolify volume snapshot is not a substitute for a dump you have verified you can restore.
